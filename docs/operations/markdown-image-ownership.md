# 업로드 파일 소유권과 정리 (#88, #93)

본문 편집기(`/api/upload-image`)와 교수진·갤러리·가이드북·강의자료·수료생 이야기 서버 액션이 새로 업로드한 파일만 `markdown_image_assets`에 기록합니다. 테이블 이름은 기존 #88 스키마를 유지합니다. 기존 URL은 업로드 주체를 증명할 수 없으므로 자동 등록하거나 삭제하지 않습니다. `markdown_image_references` 뷰는 현재 DB에 저장된 본문과 직접 URL 필드를 읽어 파일의 참조처를 계산합니다. 두 콘텐츠가 같은 URL을 사용하면 두 참조가 모두 사라질 때까지 정리 후보가 되지 않습니다.

## 적용 순서

1. 격리 DB에서 `npm run db:migrate-add-markdown-image-assets`를 실행하고 테이블·뷰 및 기존 콘텐츠 조회를 확인합니다.
2. 운영 적용 전 DB 백업·스키마 차이를 검토하고, **애플리케이션 배포 전에** 같은 마이그레이션을 적용합니다. 새 업로드 API는 원장이 없으면 업로드를 실패 처리합니다.
3. 배포 후 `npm run blob:cleanup-markdown-images`로 후보 수만 확인합니다. 기본 명령은 파일을 삭제하지 않습니다.
4. 실제 정리는 콘텐츠 쓰기를 중단하고 진행 중인 쓰기가 끝난 유지보수 시간에만 `HRA_CONTENT_WRITES_STOPPED=1 npm run blob:cleanup-markdown-images -- --apply`로 실행합니다. 환경 플래그는 쓰기 중단을 자동으로 보장하지 않으므로 운영자가 이를 확인해야 합니다.

## 정리 경계

- 원장에 등록됐고 업로드 후 30일이 지났으며 현재 참조가 없는 파일만 최대 100개씩 검사합니다. 삭제 직전에 참조를 다시 확인합니다.
- 신규 업로드는 콘텐츠 행을 쓰기 전에 원장에 기록합니다. 콘텐츠 쓰기가 실패하거나 0행으로 끝나도 즉시 파일을 지우지 않습니다. DB 응답 오류 뒤 실제 커밋 여부가 불확실하기 때문입니다. 미참조 신규 파일과 DB 변경 후 미참조가 된 이전 파일은 같은 유지보수 정리에서 처리합니다.
- 기존 미등록 Blob은 콘텐츠 행을 삭제하거나 파일을 교체해도 자동 삭제하지 않습니다. URL이나 저장소 도메인만으로 소유권을 판단하지 않습니다.
- `del()` 실패 시 원장을 삭제 완료로 표시하지 않아 다음 실행에서 다시 확인할 수 있습니다. 삭제 후 원장 갱신이 실패한 경우에도 재실행 전에 Blob 상태를 확인해야 합니다.
- 운영 파일 삭제나 마이그레이션을 개발·테스트 과정에서 실행하지 않습니다. 테스트는 임시 PostgreSQL과 Blob 가짜 구현을 사용합니다.
- 새로운 본문/URL 필드를 추가할 때 참조 뷰에 해당 필드를 포함해야 합니다. 누락하면 자동 정리 대상 판단이 잘못될 수 있으므로 정리 전 뷰를 점검합니다.
