# 업로드 파일 소유권과 정리 (#88, #93)

DB에 글이 없어진 뒤에도 Blob 파일은 남을 수 있습니다. 반대로 한 파일을 여러 글이 함께 쓰고 있을 수도 있습니다. 이 문서는 **서버가 등록한 파일인지, 현재 어느 콘텐츠가 사용하는지 확인한 뒤 정리하는 방법**을 설명합니다.

## 원장과 참조 뷰

| 용어·객체 | 의미 | 정리에서 하는 일 |
| --- | --- | --- |
| 소유권 원장 `markdown_image_assets` | 서버가 새 업로드를 등록한 기록 | 임의의 URL을 삭제 대상으로 삼지 않게 함 |
| 참조 | 글·첨부 데이터가 파일 URL을 사용함 | 사용 중인 파일을 보존 |
| 참조 뷰 `markdown_image_references` | 현재 본문·직접 URL 필드에서 참조를 계산하는 조회 | 후보 선정과 삭제 직전의 사용 여부 확인 |
| GC | 더 이상 사용하지 않는 파일을 정리하는 작업 | 저장소 정리; 사용자 데이터 삭제 정책과 구분 |

테이블 이름은 기존 #88 스키마를 유지하며 이미지 외 첨부도 기록할 수 있습니다. 일반 업로드의 등록은 `recordOwnedBlob`과 기능별 업로드 기록 코드가 담당합니다. 이 문서의 정책만으로 모든 업로드 경로가 이미 원장에 통합됐다고 판단하지 않습니다. 새 경로·교체 경로를 구현할 때 등록과 참조 뷰 반영을 함께 확인합니다.

일반 정리에서는 기존 URL을 이름·도메인만 보고 소급 등록하거나 삭제하지 않습니다. 보호 자료 이전처럼 출처 확인과 기록을 수행하는 별도 마이그레이션은 해당 [파일 접근 정책](../resource-file-access-policy.md)을 따릅니다. 두 콘텐츠가 같은 URL을 사용하면 두 참조가 모두 사라지기 전에는 정리 후보가 되지 않습니다.

## 1. DB 준비와 배포

1. [DB 변경 절차](../developer/database-change-procedure.md)에 따라 `npm run db:migrate-add-markdown-image-assets`로 설치 계획을 확인합니다. `.env` 없이 실행할 수 있으며 DB에는 접속하지 않습니다. `--confirm-apply`도 신뢰된 대상·복구·승인 경계가 없어 접속 전에 차단합니다.
2. 기존 DB의 관계 종류 사전 확인, 원장 테이블·인덱스·참조 뷰 결합 설치와 후조건 조회를 수행하던 CLI는 비활성입니다. 원본 뷰 SQL·로컬 신규 설치 후보와 격리 참조 회귀는 해당 기존 DB 업그레이드의 검증을 대신하지 않습니다. 기존 Blob URL에 소유권을 소급 부여하지 않는 원칙은 유지합니다.
3. 실제 적용은 [#280](https://github.com/yeongseon/hra-website/issues/280)의 대상·복구·승인이 검증된 기존 DB 업그레이드 절차가 마련된 뒤 진행합니다. 테이블·뷰·기존 콘텐츠 조회를 카탈로그와 합성 데이터로 검증하고 원장을 사용하는 앱보다 먼저 DB 준비를 완료해야 합니다. 필요한 객체가 없는 DB에는 관련 업로드·정리 기능을 배포하지 않습니다.
4. 배포 후 합성 파일로 등록·콘텐츠 연결을 확인합니다. 원장 등록이 필요한 경로는 원장 준비 없이 정상 업로드를 완료할 수 없습니다.

## 2. 삭제 없이 후보 확인

```bash
npm run blob:cleanup-markdown-images
```

기본 명령은 `DATABASE_URL`을 사용해 후보 수만 확인하며 실제 파일을 삭제하지 않습니다. 원장에 등록된 시각(`created_at`)을 기준으로 30일이 지났고, 삭제 완료 표시와 현재 참조가 없는 파일을 최대 100개 조회합니다. 원장 등록 시각과 실제 파일 전송 완료 시각은 항상 같지는 않습니다.

**정상 결과:** 후보 개수와 읽기 전용 점검 완료가 표시됩니다. 0개도 정상입니다. **실패하면:** 연결 DB와 테이블·뷰 준비를 확인합니다. 원장을 임의로 채워 삭제 대상을 만들지 않습니다.

## 3. 실제 정리

콘텐츠 쓰기를 중단하고 진행 중인 쓰기가 끝난 유지보수 시간에만 실행합니다. 다음 환경값은 운영자가 그 조건을 확인했다는 표시이며, **앱의 쓰기를 자동으로 잠그는 기능이 아닙니다.**

```bash
HRA_CONTENT_WRITES_STOPPED=1 npm run blob:cleanup-markdown-images -- --apply
```

실제 삭제에는 해당 환경의 `BLOB_READ_WRITE_TOKEN`이 필요합니다. 비공개 자료 후보가 있으면 `RESOURCE_PRIVATE_BLOB_HOST`와 `RESOURCE_PRIVATE_READ_WRITE_TOKEN`도 일치해야 합니다. 스크립트는 삭제 직전에 현재 참조를 다시 확인하고, 설정이 맞지 않는 비공개 파일은 삭제하지 않고 실패로 남깁니다.

| 결과 | 처리 |
| --- | --- |
| 새 참조 발견 | 보존하고 다음 후보로 이동 |
| 삭제 성공 또는 파일이 이미 없음 | 원장에 삭제 완료 표시 |
| Blob 삭제 실패 | 완료 표시를 하지 않고 실패 기록 |
| 삭제 후 DB 기록 실패 | 파일·원장 상태를 확인한 뒤 재실행 판단 |

출력되는 삭제·보존·실패 개수와 종료 상태를 확인합니다. 실패가 있으면 원인을 해결하고 다시 현재 참조를 확인합니다. 운영 파일 URL·내용을 기록하거나 자동으로 다음 100개를 연속 삭제하는 절차로 확대하지 않습니다.

## 4. 업로드·저장 실패의 처리 기준

일부 생성 경로는 콘텐츠 DB 쓰기 전에 이번 요청에서 만든 파일을 정리할 수 있습니다. 예를 들어 업로드 일부 실패나 원장 기록 실패의 즉시 정리와, **콘텐츠가 실제로 저장됐는지 불확실한 경우**는 구분해야 합니다.

DB 응답이 유실되어 커밋 여부를 알 수 없을 때에는 연결된 콘텐츠와 원장을 확인하기 전까지 파일을 보존하는 것이 기준입니다. 남은 미참조 파일은 위 유지보수 절차에서 다시 확인합니다. 모든 실패가 동일하게 즉시 삭제되거나 동일하게 영구 보존된다고 설명하지 않습니다.

새 본문·URL 필드를 추가할 때에는 `scripts/sql/markdown-image-references.sql`에 해당 참조를 반영합니다. 실제 업로드부터 게시·교체·공유 참조·삭제까지 격리 PostgreSQL과 Blob 가짜 구현으로 검증합니다.
