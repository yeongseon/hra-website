# 학사 개인정보 보존·파기 정책 초안

운영 책임자와 개인정보 처리 기능을 구현하는 개발자가 함께 읽는 승인용 문서다. 먼저 1절에서 어떤 데이터가 있는지, 2절에서 무엇을 결정해야 하는지 확인한다. **삭제를 막는 DB 제약, 미완료 업로드 정리, 개인정보 보존기간에 따른 파기는 서로 다른 기능**이다. 용어는 [용어집](getting-started/glossary.md), 실제 코드 변경 절차는 [DB 변경 절차](developer/database-change-procedure.md)를 참고한다.

## 상태와 적용 범위

**2026-10-16 기준 승인용 초안이며, #142는 미완료다.** G1의 최종 학사 관리 승인자는 사용자가 지정한 HRA 운영 책임자 본인으로 확정됐다. 저장 종류별 보존기간·기산점과 아래 운영 절차는 아직 승인되지 않았다. 이 문서의 추가는 운영 수집·삭제·백업을 활성화하거나 법적 보존기간을 확정하지 않는다.

이 문서는 G1 학생 명부, 계정 연결, 과제 대상, 개인 제출물, 감사·관측 기록과 그 사본에 적용한다. 기존 공동 자료실의 공개 범위 정책과 구분한다. 평가·교수 피드백·출결·수료 판정은 현재 G1 수집 항목이 아니며, #143과 후속 단계에서 별도로 결정한다.

아래의 **구현 사실**은 현재 코드의 동작을 뜻한다. **운영 제안**은 승인과 구현·검증이 필요한 절차다. **기관 결정 대기** 항목은 기본값이나 무기한 보존 승인으로 해석하지 않는다. 운영 개시 전 실제 보존 기준과 이를 실행할 수단을 함께 확인한다.

## 1. 데이터·목적·열람 범위 — 구현 사실

| 저장 종류 | 현재 저장하는 항목 | 사용 목적 | 현재 애플리케이션 열람 범위 |
| --- | --- | --- | --- |
| 학생 명부 | 학생 UUID, 표시 이름, 생성·변경 시각, 선택적 연결 계정 UUID | 계정 유무와 별개인 학생 식별·본인 확인 후 연결 | 지정 승인자. 학생의 과제 조회는 본인과 연결된 명부를 인가에 사용 |
| 기수 등록 | 등록·학생·기수 UUID, 등록 상태·시각, 선택적 종료 시각·승인자 UUID | 기수별 대상·현재 등록 여부 확인 | 지정 승인자. 학생은 본인의 유효 등록을 통한 과제 조회 |
| 과제·대상 | 과제·기수·생성자 UUID, 제목·안내·상태·시각, 대상 등록·승인자 UUID, 선택적 수업 연결·마감·공개 정보 | 과제 안내, 대상 확정, 제출·미제출 집계 | 지정 승인자, 본인이 대상인 공개·종료 과제의 현재 인가된 학생 |
| 업로드 의도·승인 원장 | 의도·대상·사용자·요청 UUID, 불투명 저장 키, 원본 파일명·예상 크기, 만료·상태, 단계별 처리 시각·ETag 및 검증된 MIME·크기·SHA-256 | 업로드 승인, 실물 검증, 최종화·멱등 재시도·고아 객체 정리 | 서버 처리에 사용. 원장 전체를 학생에게 공개하는 화면은 없음 |
| 최종 제출·파일 메타 | 제출·대상·제출자·의도·파일 UUID, 멱등 키·확정 시각, 저장 키·원본 파일명·MIME·크기·SHA-256 | 최종 제출 사실과 원본의 대응·무결성 확인 | 지정 승인자, 현재 인가된 본인. 집계·CSV도 지정 승인자 전용 |
| 비공개 PDF 원본 | 비어 있지 않은 PDF 1개, 최대 50MiB(52,428,800바이트) | 해당 과제 제출물 열람 | 매 요청 인가를 통과한 본인 또는 지정 승인자만 인증된 첨부 다운로드 |
| 업무 승인·변경 감사 | 행위자·대상·요청 UUID, 확인 방식·근거 참조, 승인 계획·변경 요약·지문·시각 | 등록·연결·과제 변경·제출 확정의 책임과 이력 확인 | 업무 처리 서버가 기록. 별도 전체 감사 열람 UI는 없음 |
| 파일 접근 감사 | 행위자·제출·파일 UUID, 본인/관리 열람 구분, 인가 시각 | 누가 어떤 파일에 접근 인가를 받았는지 확인 | 파일 서버가 기록. 인가 기록은 실제 수신 완료 증거가 아님 |
| 서버 관측 | 고정 작업·대상 종류·결과·시각, 서버 요청 참조, 인가 후 행위자 UUID, 검증된 대상·요청 UUID, 고정 실패 코드·재시도 정보 또는 null | 실패·거부·재시도·전송 중단 진단 | 배포 플랫폼의 별도 로그 접근 권한에 따름. 앱의 승인자 권한이 플랫폼 권한을 부여하지 않음 |
| 백업·복구 사본 | DB 덤프·스냅샷은 포함 테이블의 개인정보를 복제할 수 있음. Blob 본문 복구 사본의 실제 제공 범위는 확인 필요 | 장애 복구 | 공급자·DB·스토리지 운영 권한을 별도 확인해야 함 |
| CSV·다운로드·내보내기 사본 | 열람·내보내기로 만들어진 명부·제출 현황·원본의 사본 | 승인된 업무 수행 | 앱은 생성 요청을 인가하지만 이미 내려받은 사본의 재열람·재전달·파기를 강제하지 못함 |

학사 명부에는 별도의 전화번호·이메일 컬럼을 추가하지 않았다. 연결된 기존 회원 계정의 정보는 별도로 존재하므로, 명부만 조사해 개인정보 범위를 확정하면 안 된다. UUID·근거 참조·해시도 다른 기록과 연결될 수 있어 익명 정보로 취급하지 않는다.

**현재 인가 경계:** 지정 승인자는 실제 로그인 계정과 서버 설정 UUID가 일치하고 현재 DB 역할이 승인된 `MEMBER`·`FACULTY`·`ADMIN` 중 하나여야 한다. 학생은 현재 `MEMBER` 역할, 본인 계정 연결, 유효 기수 등록과 본인 과제 대상을 모두 확인한다. 일반 홈페이지 `ADMIN`이나 `FACULTY` 역할만으로 학사 관리·타인 파일 열람 권한을 얻지 않는다. 비로그인·`PENDING`은 거부한다. 학생의 등록 종료·연결 해제로 본인 접근이 사라져도 관리 승인자의 보존 파일 열람과 데이터 삭제는 별개다.

애플리케이션 인가는 DB·Blob·배포 플랫폼 운영자의 직접 접근을 통제하는 수단이 아니다. 운영 개시 전에 운영자 명단, 최소 권한, 권한 회수 방식과 비공개 증거 위치를 확인해야 한다.

## 2. 보존기간·기산점 — 기관 결정 대기

아래 표는 각 종류에 독립된 결정이 필요하다는 뜻이다. 빈 기간을 채우기 위해 임의의 연수·일수나 법정 의무를 가정하지 않는다. 시작 시점의 예도 승인된 기준이 아니다.

| 종류 | 보존기간 | 기산점에서 정할 사항 | 종료 시 처리에서 정할 사항 |
| --- | --- | --- | --- |
| 명부·계정 연결·기수 등록 | 기관 결정 대기 | 등록 종료·계정 탈퇴·수료 중 어떤 사건을 기준으로 삼는지 | 식별 정보 삭제/익명화와 보존 이력의 범위 |
| 과제·대상·최종 제출 메타 | 기관 결정 대기 | 과제 종료·학기 종료·판정 확정 등 기준 | 제출 사실·감사와 참조를 유지하거나 제거할 범위 |
| 최종 비공개 PDF | 기관 결정 대기 | 제출 확정·마감·검토 종료 등 기준 | 원본·복구 사본·다운로드 사본의 파기 순서와 증거 |
| 미최종화 의도·승인 원장·삭제 확인 이력 | 기관 결정 대기 | 의도 만료·최종화·정리 완료 등 상태별 기준 | 본문 정리 뒤 남기는 원장의 최소 항목과 보존 종료 |
| 업무 감사·파일 접근 감사 | 기관 결정 대기 | 사건 발생·관련 업무 종료 등 기준 | 행위자 연결·근거 참조·지문을 포함한 제거/익명화 |
| 서버 관측 로그 | 기관 결정 대기 | 이벤트 시각 기준 여부 및 플랫폼 설정 | 검색·내보내기 사본과 공급자 보존 한계 |
| DB 백업 | 기관 결정 대기 | 백업 생성 시각·주기·세대별 기준 | 만료 삭제, 개인정보 삭제 전파, 복원 시 재삭제 |
| Blob 복구 사본 | 기관 결정 대기 | 실제 복구 기능·사본 생성 방식에 맞춘 기준 | 원본과 사본의 동시/순차 파기 및 복구 가능 범위 |
| CSV·다운로드·업무 사본 | 기관 결정 대기 | 업무 완료·사본 생성 등 기준 | 담당자·저장 위치·재전달 제한·폐기 확인 |

확정할 때 각 행에 기간, 기산 사건, 담당자, 실행 수단, 예외 승인·만료와 비공개 검증 증거를 함께 남긴다. 기관의 기존 기준이나 별도 검토가 있으면 그 근거·적용 범위를 확인해 반영한다. 승인이 끝나기 전 #142를 종료하지 않는다.

## 3. 현재 보존·삭제 경계 — 구현 사실

- 주요 명부·기수·등록·제출·감사 참조는 외래키 `RESTRICT` 등으로 보호된다. 과제 공개 후 대상과 최종 제출·파일·접근 감사의 불변 조건도 존재한다. 계정·기수 삭제를 개인정보 일괄 파기로 대신할 수 없으며, 이 제약이 무기한 보존을 승인하는 것도 아니다.
- 업로드 취소는 승인 원장에 종료 시각(`retired_at`)을 기록하여 해당 의도의 최종화를 막는다. 의도 자체의 `INTENDED`·`VERIFIED` 상태를 변경하는 것은 아니다. 취소 응답이 Blob 원본의 즉시 삭제를 뜻하지 않는다.
- 고아 객체 정리는 미최종화 의도의 만료 후 5분 유예, 최종 제출·파일에서 미참조, DB 선점, 객체 ETag 일치를 모두 확인한다. 기본 비활성·기본 dry-run이며 실제 삭제에는 별도 쓰기 설정이 필요하다. **이 5분은 기술적 경합 방지 유예이며 개인정보 보존기간이 아니다.** 원본 삭제 확인 뒤 원장 자체의 보존기간은 별도 결정한다.
- 확정된 제출물의 개인정보 파기·익명화·승인 예외를 수행하는 기능은 아직 구현되지 않았다. 보존기간만 승인해도 해당 절차를 실행할 수 있게 되는 것은 아니다.
- 파일 다운로드는 인증된 서버 중계와 캐시 금지를 사용한다. 외부 뷰어·장기 유효 공개 URL 제공은 현재 범위에 없다. 업로드 승인 만료와 매 요청 열람 인가를 원본 보존기간이나 이미 내려받은 사본의 만료로 해석하지 않는다.

구현 근거: [데이터 모델](ACADEMIC-DATA-MODEL.md), [직접 업로드·정리](developer/academic-assignment-uploads.md), [개인 파일 다운로드](developer/academic-submission-files.md), [감사·관측·복구](developer/academic-observability.md). 스키마와 SQL 보호는 `src/lib/db/schema.ts`, `src/lib/db/academic-*.ts`, `scripts/migrate-academic-*.sql`에 정의되어 있다.

## 4. 개인정보 요청·예외·파기 절차 — 운영 제안, 미승인

1. **접수·본인 확인:** 요청자를 확인하고 열람·정정·삭제·계정 탈퇴 중 요청 종류와 대상 범위를 구분한다. 이메일 일치만으로 계정을 연결하거나 삭제를 승인하지 않는다. 접수 채널·담당자·응답기한은 기관이 정한다.
2. **영향 조사:** 회원 계정, 학생·기수 등록, 과제 대상·최종 제출, 비공개 본문, 승인·접근 감사, 서버 로그, 백업과 업무 사본까지 참조 관계를 확인한다. 공개 이슈에는 실명·계정 UUID·파일 키·원본·덤프를 올리지 않는다.
3. **결정·보류:** 지정 승인자가 적용 기준과 삭제/정정/유지 범위를 확인한다. 분쟁·조사 등 보류 사유를 임의로 가정하지 않는다. 예외가 필요하면 사유, 대상, 재검토 시점, 종료 조건, 승인자와 실행 담당자를 비공개로 기록한다. 기관의 추가 검토가 필요한 사안은 해당 담당자 확인을 거친다.
4. **실행 계획:** 삭제·익명화·연결 해제·열람 철회 중 필요한 조치를 구분하고 참조·감사·사본의 처리 순서를 정한다. 기존 불변 제약을 임시 해제하는 수동 삭제로 대신하지 않는다. 현재 기능으로 수행할 수 없는 처리는 별도 검토한 구현·DB 변경과 검증이 필요하다.
5. **실행·확인:** 승인 범위에서만 실행하고 처리 전후 건수, 참조 무결성, 최종물 보호, 원본·사본 처리 결과를 확인한다. 일부 사본이 남았거나 공급자 삭제가 확인되지 않았으면 완료로 보고하지 않는다.
6. **회신·종결:** 처리 결과, 남은 사본·보류와 다음 확인 시점을 요청자에게 알린다. 처리 증거 자체에 원본 개인정보를 다시 복제하지 않고, 최소한의 요청 참조·승인·결과를 승인된 비공개 위치에 남긴다. 이 증거의 보존기간도 별도로 정한다.

계정 탈퇴, 기수 삭제, 과제 종료·비공개화는 위 검토의 계기가 될 수 있으나 그 자체가 관련 기록 전체의 삭제 명령은 아니다. 학적 종료나 계정 연결 해제 기능의 구현·권한도 별도 확인한다. 외부 뷰어가 필요해지면 제공 목적·수신자·기간·회수·사본 처리를 승인받기 전 원본을 전달하지 않는다.

## 5. 백업·복원·고아 정리 — 운영 제안과 검증 경계

DB 백업은 Blob 본문을 포함하지 않는다. 현재 합성 로컬 PostgreSQL의 덤프·복원 검증은 제약과 제출 참조 보존의 증거이며, 운영 백업의 존재·설정·권한이나 Blob 원본 복구의 증거는 아니다.

운영 복구 기준에는 다음을 함께 결정하고 검증한다.

- DB·Blob 각각의 백업 담당자, 접근 권한, 보존 세대·기간, 복구 가능한 시점과 소요시간 목표, 비용·기능 한계
- 삭제 결정의 비공개 최소 기록과 복원 후 재적용 순서. 삭제 이전 백업을 복원했을 때 삭제 대상이 다시 서비스되지 않도록, 격리 복원 후 삭제·익명화·권한 철회를 재적용하고 대조한 뒤 서비스 연결
- 복원 대상의 DB 역할·함수·불변 트리거·제약·권한과 최종 제출·파일의 건수·크기·해시 대조. 운영 데이터를 테스트 대상으로 사용하거나 덤프·키·원본을 공개 출력하지 않음
- 백업 만료·삭제 전파 확인과 Blob 사본의 실제 복원 시험. 복구 사본을 만들지 않거나 본문 복구가 불가능한 경우에도 그 한계와 수용 여부를 명시적으로 결정
- CSV·다운로드 등 앱 밖 사본의 소유자·보관 위치·폐기 확인. 앱의 접근 회수만으로 외부 사본 파기가 완료됐다고 보고하지 않음

고아 정리는 **미참조 업로드 객체**만 대상으로 한다. 최종 제출 본문·감사·백업의 보존기간을 집행하는 수단으로 확장하지 않는다. 보존·보류 대상과 정리 대상이 충돌하면 실행을 멈추고 승인자에게 확인한다. 승인된 개인정보 파기 절차는 고아 정리와 별도로 설계·검증한다.

구체적인 복원 확인 순서는 [운영 복구 절차](developer/academic-observability.md), DB 변경은 [데이터베이스 변경 절차](developer/database-change-procedure.md)를 따른다. #157의 남은 운영 확인은 위 기준 확정과 실제 설정·복구 검증까지 완료한 뒤 판단한다.
