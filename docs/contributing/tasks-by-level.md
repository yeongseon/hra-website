# 난이도별 작업 가이드

작업은 익숙한 기술과 **영향 범위**를 함께 보고 고릅니다. 같은 한 줄 변경이라도 권한이나 DB에 닿으면 숙련된 리뷰어가 필요합니다. 먼저 [협업 절차](workflow.md)에 따라 기존 이슈와 완료 조건을 확인합니다.

## 1. 작은 범위부터 시작하기

프로그래밍 경험이 많지 않다면 변경 전후를 눈으로 비교하고 설명할 수 있는 작업이 좋습니다.

| 작업 | 시작 위치 | 완료 확인 |
| --- | --- | --- |
| 개발 문서의 오타·끊어진 링크 수정 | `docs/`의 해당 문서 | 설명과 명령이 현재 코드에 맞고 링크가 열립니다. |
| 코드에 직접 적힌 짧은 한국어 문구 수정 | 해당 페이지나 컴포넌트 | 화면의 뜻이 정확하고 작은 화면에서도 잘림 없이 보입니다. |
| 재현 가능한 버그 제보 | GitHub 이슈 | 사용 환경·순서·기대 결과·실제 결과를 다른 사람이 따라갈 수 있습니다. |
| 정적 로고 등 이미지 교체 | 실제 참조하는 `public/` 파일 | 사용 권한·크기·대체 텍스트를 확인하고 모든 사용 위치가 정상입니다. |

공지사항 작성·교수진 정보 수정은 일반적으로 **운영 콘텐츠 관리**입니다. 승인된 관리자가 관리자 화면에서 처리하며, 새 공지를 `content/notices/`에 추가하거나 교수 정보를 코드에 다시 하드코딩하지 않습니다. 연습은 개발 환경에서 합니다.

## 2. 화면 구조를 이해한 뒤 할 작업

**HTML**은 문서 구조, **CSS**는 화면 표현을 정하는 기술입니다. 기존 컴포넌트를 읽고 작은 화면과 키보드 조작을 확인할 수 있다면 다음 작업을 진행할 수 있습니다.

| 작업 | 필요한 이해 | 완료 확인 |
| --- | --- | --- |
| 여백·글자 크기·배치 조정 | Tailwind 클래스와 반응형 화면 | 모바일·데스크톱에서 읽기와 조작이 가능합니다. |
| 공개 안내 페이지 추가 | Next.js 페이지 경로와 공통 레이아웃 | 주소·제목·메뉴·없는 페이지 처리가 자연스럽습니다. |
| 입력 안내·오류 표시 개선 | 폼 상태와 접근성 | 키보드와 보조 기술로 입력 오류를 이해할 수 있습니다. |
| 공통 UI 개선 | 사용하는 여러 화면의 영향 | 해당 부품을 쓰는 주요 화면의 동작이 유지됩니다. |

공통 버튼이나 입력창은 여러 기능에 영향을 줍니다. 변경할 파일 수가 적어도 사용 위치를 먼저 찾습니다. 새 페이지에서 보호 데이터를 다룬다면 화면 작업 범위를 넘어가므로 서버 권한 검토를 포함합니다.

## 3. 데이터·권한·운영에 닿는 작업

다음 작업은 관련 정책과 실패 시 복구 방법을 이해한 뒤 담당 리뷰어와 진행합니다.

| 작업 | 먼저 확인할 문서 | 검증의 중심 |
| --- | --- | --- |
| 인증·권한 수정 | [AGENTS.md](https://github.com/yeongseon/hra-website/blob/main/AGENTS.md), 해당 기능 정책 | 허용·거부 조건, 기존 계정과 세션의 영향 |
| DB 구조·저장 로직 변경 | [DB 변경 절차](../developer/database-change-procedure.md) | 기존 데이터, 제약, 동시 요청, 적용·복구 |
| 업로드·다운로드 변경 | [자료 접근 정책](../resource-access-policy.md), [파일 접근 정책](../resource-file-access-policy.md) | 권한, 파일 검증, 저장소 접근, 실패 후 정리 |
| 신규 API·공용 업무 로직 | [플랫폼 아키텍처](../developer/platform-architecture.md) | 입력·응답 계약, Service와 Repository 경계 |
| 학사 기능 | [학사관리 로드맵](../ACADEMIC-MANAGEMENT-ROADMAP.md) | 결정된 정책, 기능 설정, 기수·학생별 접근 권한 |
| 배포·CI 변경 | [품질 게이트](../QUALITY-GATE.md) | 운영 비밀값 분리, 자동 검사와 배포 후 확인 |

API는 다른 프로그램이 서버 기능을 호출하는 접점입니다. 목표 구조의 `/api/v1`, 공용 계약, `apps/mobile`은 기반 전환 상태를 확인한 뒤 착수합니다. 현재 모든 API·모바일 구조가 준비되어 있다고 가정하지 않습니다. Android/iOS는 [플랫폼 계획](../PLATFORM-ROADMAP.md)에 따라 React Native와 Expo를 사용하는 하나의 앱 코드로 진행할 목표입니다.

## 4. 작업을 마쳤는지 판단하기

PR에는 “수정했다”는 말과 함께 **무엇을 확인했는지**를 적습니다.

- 문서·화면 변경: 실제 경로와 내용, 화면·링크 확인 결과
- 동작 변경: 정상·오류·권한 거부 경우의 확인 결과
- DB·운영 변경: 적용 전제, 데이터 영향, 남은 적용·복구·운영 확인
- 테스트: 실행한 명령과 결과, 실행하지 못한 항목과 이유

AI를 사용해도 이 완료 기준은 같습니다. 도움을 요청하는 방법은 [AI 도구 활용](ai-tools.md), 검사 명령은 [빌드·배포 가이드](build-and-deploy-safety.md)를 참고합니다.
