# 협업 워크플로우 — 이슈부터 완료까지

작업 관리는 **GitHub 이슈 → 작업 브랜치 → PR → CI·리뷰 → 완료 확인**으로 합니다. 별도의 프로젝트 보드나 마일스톤은 필요하지 않습니다.

## 1. 이슈로 작업 정하기

기능, 버그, 보안, 데이터, 배포에 영향을 주는 작업은 먼저 [열린 이슈](https://github.com/yeongseon/hra-website/issues)를 검색합니다. 같은 문제가 있으면 새로 만들지 말고 그 이슈에 새로 확인한 사실만 댓글로 남깁니다. 없으면 아래 세 가지 폼 중 하나로 만듭니다. 단일 오타·문구 수정은 이슈 없이 PR에 이유를 적어도 됩니다.

제목에는 요약만 적습니다. `[P1]`, `[보안]` 같은 대괄호 접두어를 쓰지 않고, 종류·우선순위·분류는 모두 **라벨**로 표시합니다. 라벨은 목록에서 고르므로 값이 흩어지지 않고, `label:P1 label:보안` 처럼 바로 걸러 볼 수 있으며, 우선순위를 바꿀 때 제목을 고칠 필요가 없습니다.

| 종류 | 종류 라벨 | 우선순위 라벨 | 분류 라벨 | 본문 섹션 (`###`, 이 순서) |
| --- | --- | --- | --- | --- |
| 버그 | `bug` | 하나 | 하나 | 문제와 기대 결과 → 재현 근거와 영향 → 완료 조건 → 관련 이슈 |
| 작업 | `enhancement` | 하나 | 하나 | 목표 → 근거와 범위 → 완료 조건 → 관련 이슈 |
| 정책 확인 | `question` | 없음 | 없음 | 목표 → 근거와 범위 → 완료 조건 → 관련 이슈 |
| 추적 | `추적` | 없음 | 없음 | 자유 형식. `- [ ] #번호` 체크리스트 필수 |

- **종류 라벨**은 정확히 하나만 붙입니다.
- **우선순위 라벨**: `P1`은 보안 경계, 데이터 유실, 서비스 중단처럼 먼저 처리할 문제이고 `P2`는 그 외 작업입니다. `P0`는 비공개로 다루는 긴급 보안 건에만 씁니다.
- **분류 라벨**은 다음 일곱 가지 중 하나만 붙입니다. 목록에 없는 라벨을 새로 만들지 않습니다.

    | 분류 | 쓰는 경우 |
    | --- | --- |
    | `보안` | 인증·권한·요청 제한·정보 노출 |
    | `무결성` | 데이터 유실·부분 저장·경합·삭제 순서 |
    | `검증` | 서버 입력값 검증 누락 |
    | `업로드` | 파일 업로드와 Blob 저장 |
    | `기능` | 화면·동작이 의도와 다른 그 밖의 버그와 기능 변경 |
    | `접근성` | 키보드·스크린 리더 사용 |
    | `품질` | 테스트·CI·스크립트·문서·저장소 설정 |

- 진행 상태를 나타내는 라벨은 만들지 않습니다. 상태는 담당자 지정과 열림/닫힘으로 봅니다.
- **한 이슈에는 한 가지 결과만** 적습니다. 원인이 같아 함께 고쳐야 하는 경우만 묶습니다.
- **완료 조건**은 `- [ ]` 체크리스트로, 닫아도 되는지 다른 사람이 확인할 수 있게 적습니다.
- **확인 수준**을 적습니다. 직접 재현했는지, 코드로만 확인했는지, 확인하지 못한 전제가 무엇인지 구분합니다.
- 요구사항 자체가 미정이면 정책 확인 이슈로 등록해 결정을 기록한 뒤 구현합니다.
- 공개 저장소입니다. 개인정보, 실제 자료 URL, 공격 코드는 올리지 않습니다. 악용 가능한 취약점은 공개 이슈 대신 [비공개 보안 권고](https://github.com/yeongseon/hra-website/security/advisories/new)로 등록합니다.
- 리뷰 결과처럼 이슈를 여러 개 만들었다면 `추적` 라벨이 붙은 이슈의 체크리스트에 추가합니다. 추적 이슈가 전체 목록의 기준입니다.

**형식은 자동으로 검사합니다.** 웹 화면의 폼은 본문 구조와 종류 라벨을 만들어 주지만 분류 라벨은 직접 골라야 하고, `gh issue create`나 API, 자동화 도구로 만든 이슈는 폼을 거치지 않습니다. 그래서 이슈가 만들어지거나 수정될 때마다 [이슈·PR 형식 검사](https://github.com/yeongseon/hra-website/actions/workflows/process-format.yml)가 실행되어, 형식이 다르면 고칠 항목을 이슈에 댓글로 남깁니다. 고치면 댓글이 통과로 바뀝니다. 명령줄로 이슈를 만들었다면 바로 확인합니다.

```bash
npm run issues:check   # 열린 이슈 전체의 제목·라벨·본문 구조 검사

# 명령줄로 만들 때의 예
gh issue create --title "요약" --label bug --label P2 --label 기능 --body-file 본문.md
```

규칙의 정의는 `scripts/_lib/process-format.mjs` 한 곳입니다. 폼(`.github/ISSUE_TEMPLATE/*.yml`), PR 템플릿, 이 문서의 표를 바꿀 때는 그 파일도 함께 바꿉니다. 어긋나면 단위 테스트(`tests/unit/process-format.test.ts`)가 실패합니다.

**착수할 때** 담당자 한 명을 지정합니다. 담당자가 없는 열린 이슈는 대기 중인 작업입니다. 막히면 이슈 댓글에 막힌 이유와 다음 필요한 결정을 남깁니다.

## 2. 작업 브랜치와 PR

`main`에서 직접 작업하지 말고, 최신 `main`에서 브랜치를 만듭니다.

```bash
git switch main
git pull origin main
git switch -c fix/issue-번호-짧은설명
```

새 기능은 `feature/`, 버그는 `fix/`, 문서는 `docs/`로 시작합니다. PR은 템플릿의 네 섹션(관련 이슈, 변경 내용, 검증 결과, 배포 영향과 리뷰)을 지우지 않고 채웁니다. 관련 이슈에는 `Closes #번호`나 `Refs #번호`를, 이슈가 없는 변경이면 `이슈 없음: 사유`를 적습니다. 이 형식도 PR마다 자동으로 검사합니다. 병합만으로 완료되는 작업은 `Closes #번호`를 사용합니다. **DB 마이그레이션이나 운영 확인이 남으면** `Refs #번호`를 사용하고, 적용 확인 후 이슈를 닫습니다.

한 사람은 진행 중인 작업을 가급적 하나씩 맡습니다. 새 일을 시작하기 전에 현재 PR을 완료하거나 이슈에 중단 이유를 남깁니다.

## 3. 검증과 리뷰

현재 [CI](https://github.com/yeongseon/hra-website/actions/workflows/ci.yml)는 PR과 `main` 푸시에서 **lint → typecheck → Vitest → build**를 실행합니다. PR에서 실패한 검사를 원인 확인 없이 건너뛰지 않습니다.

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

인증·라우팅 등 브라우저 동작을 바꿨다면 `npm run test:e2e`와 실제 화면도 확인합니다. 결과나 미실행 사유를 PR에 남깁니다. 로컬 훅은 커밋 전 타입 검사, 푸시 전 빌드를 실행합니다. 훅을 우회하지 않습니다. 의미 있는 변경은 [AGENTS.md §11](https://github.com/yeongseon/hra-website/blob/main/AGENTS.md#11-코드-리뷰-정책-oracle-필수)의 Oracle 리뷰 조건도 적용합니다.

리뷰어는 이슈의 완료 조건, 권한·데이터 영향, 검증 증거를 확인합니다. CI와 필요한 리뷰가 끝난 뒤 병합합니다. 현재 저장소에는 `main` 브랜치 보호 규칙이 없으므로 이 확인은 PR 작성자와 리뷰어가 직접 지켜야 합니다.

## 4. 완료와 주간 정리

이슈는 완료 조건을 확인하고 PR이 병합된 뒤 닫습니다. 배포·마이그레이션이 포함되면 적용 결과까지 확인합니다. 매주 열린 이슈를 짧게 훑어 중복을 닫고, `npm run issues:check`로 형식을 확인하고, `추적` 이슈의 체크리스트를 실제 상태와 맞춘 뒤, `P1`부터 다음 작업의 담당자를 정합니다. 아직 결정되지 않은 정책은 구현 이슈보다 먼저 결정합니다.

빌드·배포 시 주의할 점은 [빌드·배포 안전 가이드](build-and-deploy-safety.md)를 참고합니다.
