# AI 도구로 기여하기

AI 도구는 코드의 의미를 설명하거나 변경 초안을 만드는 데 사용할 수 있습니다. 이 문서는 OpenCode·Codex·Claude 등 어떤 도구를 사용하든 HRA의 작업 범위와 검증 기준을 지키는 방법을 설명합니다.

## 1. 도구의 작업 범위 확인하기

시작하기 전에 도구가 **무엇을 읽고 어디에 쓸 수 있는지** 확인합니다.

| 사용 방식 | 제공해야 할 맥락 | 결과 확인 |
| --- | --- | --- |
| 대화에 코드 일부를 붙여 질문 | 파일의 역할, 관련 타입·호출부, 알고 싶은 점 | 설명이 실제 코드와 맞는지 확인합니다. |
| 로컬 폴더를 읽고 수정하는 에이전트 | 대상 저장소·브랜치, `AGENTS.md`, 관련 이슈와 문서 | 변경 파일과 diff, 실행한 검사를 확인합니다. |
| GitHub에서 작업을 맡기는 에이전트 | 저장소 접근 권한, 이슈 범위와 완료 조건 | 생성된 브랜치·PR, CI, 리뷰 결과를 확인합니다. |

도구를 설치하거나 연결할 때는 팀이 승인한 계정과 공식 안내를 사용합니다. OpenCode의 설치·실행은 [공식 문서](https://opencode.ai/docs/)를 참고합니다. 요금·지원 기능·저장소 접근 권한은 계정과 설정에 따라 달라지므로 이 문서에서 일괄 보장하지 않습니다.

GitHub Copilot에 작업을 맡기는 기능을 사용한다면 저장소에서 활성화되어 있는지 확인하고 [GitHub의 공식 작업 시작 절차](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/start-copilot-sessions)를 따릅니다. `copilot` 라벨을 새로 붙이면 자동으로 시작된다고 가정하지 않습니다. 이 저장소의 이슈 라벨은 [협업 절차](workflow.md)에 정의된 목록을 사용합니다.

## 2. 작은 결과 하나를 요청하기

요청에는 목적, 대상, 범위, 완료 조건을 함께 적습니다. 파일 이름은 실제 저장소에서 확인한 경로를 사용합니다.

```text
HRA 저장소의 AGENTS.md와 관련 문서를 먼저 읽어 주세요.

목표: 작은 화면에서 푸터 연락처를 읽기 쉽게 바꿉니다.
대상: src/components/layout/footer.tsx와 실제 사용되는 스타일
범위: 레이아웃과 줄바꿈만 조정합니다. 연락처 값은 변경하지 않습니다.
완료 조건:
- 작은 화면과 데스크톱에서 내용이 잘리지 않습니다.
- 키보드로 링크를 사용할 수 있습니다.
- 변경 이유와 실행한 검사, 미실행 검사를 설명해 주세요.
알아야 할 정보가 코드에 없으면 추측하지 말고 필요한 확인을 알려 주세요.
```

“사이트를 전부 개선해 줘”처럼 결과를 판단하기 어려운 요청보다, 완료 여부를 확인할 수 있는 작은 작업이 검토하기 쉽습니다.

운영 콘텐츠를 바꾸려는 경우에는 코드 수정이 필요한지 먼저 확인합니다. 교수진·공지·모집 정보처럼 관리자 화면에서 관리하는 데이터를 파일에 하드코딩하도록 요청하지 않습니다.

## 3. 이슈와 작업 브랜치 준비하기

관련 이슈가 있는지 먼저 검색합니다. 새 작업 이슈를 만든다면 저장소 폼을 사용하고 네 섹션을 유지합니다. 예를 들어 작업 이슈는 다음 구조입니다.

```markdown
### 목표

작은 화면에서도 푸터 연락처를 읽고 링크를 선택할 수 있게 합니다.

### 근거와 범위

현재 화면과 footer.tsx를 확인하고 줄바꿈·간격을 조정합니다.
실제 연락처 값은 바꾸지 않습니다.

### 완료 조건

- [ ] 작은 화면과 데스크톱에서 잘림이 없습니다.
- [ ] 키보드로 링크를 선택하고 이동할 수 있습니다.
- [ ] 변경 범위에 필요한 검사 결과를 PR에 기록합니다.

### 관련 이슈

없음
```

종류·우선순위·분류 라벨은 [협업 절차](workflow.md)에 따라 선택합니다. 명령줄이나 API로 이슈를 작성했다면 `npm run issues:check`로 확인합니다.

코드 작업은 최신 기준 브랜치에서 만든 작업 브랜치에서 진행합니다. AI가 다른 사람의 수정이나 작업 범위 밖 파일을 변경하지 않았는지 확인합니다.

## 4. 결과를 검토하고 검증하기

AI가 완료했다고 말하면 다음 순서로 확인합니다.

1. `git status --short`로 변경 파일 목록을 봅니다.
2. `git diff`로 실제 수정 내용을 읽고 이슈의 범위와 비교합니다.
3. 화면을 바꿨다면 개발 환경에서 해당 화면과 영향을 받는 화면을 봅니다.
4. [빌드·배포 가이드](build-and-deploy-safety.md)의 검사와 변경에 필요한 테스트를 실행합니다.
5. 설명하기 어려운 코드나 이해하지 못한 권한·DB 변경이 있으면 해당 분야 리뷰어에게 확인받습니다.
6. 실제 결과와 미확인 항목을 PR에 적고 CI와 필요한 리뷰를 완료합니다.

타입 오류를 숨기는 `as any`, `@ts-ignore`, `@ts-expect-error`나 비어 있는 `catch`를 추가하지 않습니다. UI와 코드 주석은 한국어로 작성하고, 새 코드는 현재 목표 아키텍처의 경계를 따릅니다.

**OpenCode로 수행한 의미 있는 작업**에는 [AGENTS.md §11](https://github.com/yeongseon/hra-website/blob/main/AGENTS.md)의 Oracle 리뷰가 필요합니다. README·문서만 바꾸는 등 명시된 간단 변경은 면제입니다. **Claude 또는 Codex만 사용한 작업에는 Oracle 절차를 적용하지 않으며**, 빌드·테스트·CI와 일반 코드 리뷰는 계속 수행합니다. Oracle이 필요한 작업이라면 결과가 도착하기 전에 커밋·푸시하지 않습니다.

## 5. 자료를 공유하거나 막혔을 때

`.env`, 비밀번호, API 토큰, 실제 회원·지원자 정보, 보호 자료의 원본 URL을 대화나 공개 이슈에 붙이지 않습니다. 오류를 설명할 때는 민감한 값을 제거하고 실행 명령·파일·행·재현 순서를 제공합니다.

악용 가능한 보안 문제는 공개 이슈에 자세히 적지 않고 [비공개 보안 권고](https://github.com/yeongseon/hra-website/security/advisories/new)로 다룹니다.

네트워크·권한·DB 준비 부족으로 검사를 실행하지 못했다면 그 사실과 필요한 조건을 기록합니다. 통과하지 않은 검사를 통과로 바꾸거나 승인되지 않은 운영 작업으로 대신하지 않습니다. 외부 서비스 설정·DB 변경·배포가 남았다면 PR에 `Refs #번호`로 연결하고 실제 완료 조건이 충족된 뒤 이슈를 닫습니다.
