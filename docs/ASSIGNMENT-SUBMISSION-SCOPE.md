# 학생 과제 제출 기능 — 1차 범위 초안

## 목표

HRA 사이트를 간단한 학사관리 시스템으로 확장할 때, 첫 번째 기능은 **학생이 과제를 제출하고 운영진이 학생별 제출 여부를 확인하는 것**이다. 대학교 학사시스템의 모든 기능을 한 번에 도입하지 않는다.

이 문서는 기능 범위를 정하기 위한 초안이다. 아래의 **확정된 방향**과 **구현 전 결정할 사항**을 구분한다. 현재 구현된 기능을 설명하는 운영 가이드는 아니다.

## 확정된 방향

- 과제 업로드의 주체는 **학생**이다. 학생이 자신의 결과물을 제출한다.
- 제출 내역은 학생 개인과 연결되어야 한다. 운영진은 과제별로 누가 제출했는지 확인할 수 있어야 한다.
- 기존 `주차별 텍스트`와 `수업일지`는 기수에 공유하는 자료이므로, 학생별 과제 제출 내역으로 간주하지 않는다.
- 첫 단계는 과제 제출에 집중한다. 성적, 출석, 휴학·복학·수료 등 학적 상태 관리는 이번 범위에 넣지 않는다.

## 현재 코드와의 차이

| 현재 기능 | 확인된 상태 | 과제 제출에 필요한 차이 |
|---|---|---|
| 회원·기수 | `users.role`, `users.cohortId`로 접근 권한과 현재 기수를 관리한다. | 학생이 자기 기수의 과제와 **자기 제출 내역**만 볼 수 있어야 한다. |
| 주차별 텍스트 | 회원이 기수별 자료를 업로드한다. `weeklyTexts`에는 제출 학생이나 과제와의 연결이 없다. | 학생별 제출 기록을 별도로 저장해야 한다. |
| 수업일지 | 작성자 `authorId`를 기록하지만 기수에 공유하는 수업 기록이다. | 과제·제출 상태·제출 파일을 연결하는 별도 흐름이 필요하다. |
| 일정 | 수업 설명에 과제를 적을 수 있다. | 설명 문구만으로는 학생별 제출 여부를 집계할 수 없다. |

관련 코드: `src/lib/db/schema.ts`, `src/features/weekly-texts/actions/index.ts`, `src/features/class-logs/actions/index.ts`, `src/app/(member)/resources/weekly-texts/page.tsx`.

## 제안하는 최소 사용 흐름

아래는 구현을 시작하기 위한 **제안 범위**다. 운영진의 과제 등록 방식 등은 아직 최종 확정되지 않았다.

1. 운영진이 과제의 제목, 안내, 대상 기수, 마감일을 등록한다.
2. 해당 기수의 학생은 `내 과제`에서 과제와 마감일을 확인한다.
3. 학생은 파일을 제출하고 자신의 제출 시각·파일·제출 상태를 확인한다.
4. 운영진은 과제별 대상 학생 목록에서 미제출·제출 여부를 확인하고 제출 파일을 열람한다.

최소 데이터 단위는 **과제**, **학생**, **학생의 과제 제출 기록**이다. 파일 자체와 제출 기록을 분리해, 파일이 누구의 어떤 과제 제출물인지 추적할 수 있어야 한다.

## 완료 기준 초안

- 다른 기수 학생에게는 대상 과제가 보이지 않고 제출할 수도 없다.
- 학생은 다른 학생의 제출 내역이나 파일을 볼 수 없다.
- 운영진은 과제별 대상 학생의 제출 여부를 확인할 수 있다. 제출이 없는 학생도 목록에 나타난다.
- 업로드 실패 시 제출 완료로 표시되지 않는다. 제출 성공 시 학생 화면과 운영진 화면에 같은 결과가 보인다.
- 제출 파일은 URL을 아는 것만으로 열리지 않도록 접근 권한을 확인한다. 기존 자료실의 공개 Blob URL 방식을 학생 제출물에 그대로 적용하지 않는다.

## 이번 범위에서 제외

성적·평가, 피드백, 재제출 이력, 출석, 학적 상태 변경, 학생별 성적표, 알림은 첫 버전의 필수 기능으로 잡지 않는다. 필요해지면 별도 범위로 정의한다.

**후속 출결 운영의 확인된 사실:** 교수는 출결 담당자가 아니다. HRA 수업에는 **어드바이저(Advisor)**라는 별도 운영자가 있다. 출결은 G2에서 Advisor의 수업별 배정과 권한을 기반으로 추가한다. 과제 평가를 담당할 수 있는 교수진과 출결을 운영하는 Advisor는 별개다. 세부 배정·정정·승인 규칙은 [#143](https://github.com/yeongseon/hra-website/issues/143), 업무 권한 구현은 [#165](https://github.com/yeongseon/hra-website/issues/165)로 추적한다. 이 사실이 G1 과제 제출 MVP의 범위를 확장하지는 않는다.

## 구현 전 결정할 사항

| 항목 | 결정이 필요한 이유 |
|---|---|
| 제출 형식·크기·개수 | 파일 한 개만 받을지, 여러 파일이나 본문 작성도 허용할지에 따라 저장 구조와 화면이 달라진다. |
| 마감 후 제출 | 차단할지, 지각으로 표시하며 허용할지 운영 기준이 필요하다. |
| 제출물 교체 | 제출 후 수정·재제출을 허용할지, 이전 파일을 보존할지 정해야 한다. |
| 검토 권한 | 관리자만 확인할지, 교수진도 담당 과제를 확인할지 정해야 한다. |
| 대상 학생 기준 | 현재 기수에 속한 회원 전체를 대상으로 할지, 별도 수강·등록 명단을 둘지 정해야 한다. |

이 결정이 끝나면 데이터 구조와 학생·운영진 화면을 구체화한다.

## 1차 MVP 상세 실행 계약 (2026-10-13 보강)

이하 내용은 기존 `확정된 방향`을 바꾸지 않는 **구현 제안 및 수용 기준**이다. 위 표의 미확정 운영 정책을 임의로 확정하지 않는다.
전체 순서와 후속 G2/G3는 [학사관리 전환 로드맵](ACADEMIC-MANAGEMENT-ROADMAP.md), 신규 테이블·DB 제약·마이그레이션은 [학사 데이터 모델](ACADEMIC-DATA-MODEL.md)을 따른다.

### 1. 기수별 등록 학생과 제출 대상

- G1에서는 과제 제출에 필요한 최소 학생 식별·기수 등록(`academic_students`, `cohort_enrollments`)만 도입한다. **학적 상태 전환/휴학/수료 판정은 G1 범위가 아니다.**
- 로그인 계정과 학적은 별도다. 운영진이 확인하지 않은 지원서/이메일 일치만으로 학적을 자동 연결하거나 `MEMBER`로 승격시키지 않는다.
- 과제 공개 시 해당 기수의 **대상 학생 목록을 확정**하는 `assignment_targets` 방식을 우선 제안한다. 과제 발행 후 대상 학생을 추가/제외할 수 있는지 정책이 결정되어야 한다.
- 운영진의 미제출 명단은 `대상 학생 LEFT JOIN 최종 제출`을 기준으로 한다. 학생이 과제를 한 번도 열지 않아도 미제출 명단에서 누락되지 않는다.
- 학생의 공개 자료 `weekly_texts`/수업일지 `class_logs` 업로드 성공을 이 과제의 제출로 계산하지 않는다.

### 2. 과제 등록·공개 (운영진)

| 입력 | G1 계약(제안) | 서버 검증 |
| --- | --- | --- |
| 대상 기수 | 기존 `cohorts.id` 한 개 | 존재·상태·관리 권한 확인 |
| 과제 제목 | 필수 | 공백 제거·길이 상한 |
| 과제 안내 | 텍스트/마크다운, 선택 | 길이 상한·렌더링 sanitize |
| 수업 연결 | 기존 `schedule_events.id` 선택 | 해당 수업의 기수 일치 검사 |
| 마감 시각 | 선택 또는 필수는 D4에서 확정 | `Asia/Seoul` 해석·저장/표시 일치 |
| 공개 상태 | `DRAFT` → `PUBLISHED` | 공개 시 대상 학생 확정, 재공개 멱등성 |

- 다른 기수나 비공개 과제의 URL을 직접 호출해도 조회·제출할 수 없어야 한다.
- 제출자가 존재하는 과제의 삭제·대상 변경은 기본적으로 차단하고, 데이터 보존 정책에 따른 비활성화를 우선한다.

### 3. 학생의 제출 흐름

1. 서버에서 로그인, `MEMBER` 권한, 검증된 `academic_students.user_id`, 해당 과제의 `assignment_targets` 포함 여부를 확인한다.
2. 학생의 UI에는 공개된 자기 기수의 과제와 마감·상태만 표시한다. 타 학생 이름·제출 파일·관리자 내부 상태를 내려주지 않는다.
3. 서버에서 파일 형식·개수·크기·업로드 대상/만료시간을 검증한 뒤 임시 업로드 의도를 발급한다. 클라이언트가 제출한 임의 파일 URL로 최종 저장하지 않는다.
4. 업로드 성공 후 저장 객체와 의도의 매칭을 재검증하여 최종 제출을 확정한다. **파일 업로드 성공만으로 제출 완료 UI를 띄우지 않는다.**
5. 제출 확정은 `submission_key`로 멱등하게 처리한다. 응답이 유실되면 재조회/재시도로 기존 제출 결과가 복구되어야 한다.
6. 학생은 최종 제출 시각·파일명·상태를 확인한다. 파일 열람은 매 요청별 서버 접근 검증을 거친다.

### 4. 제출 상태 및 오류 시나리오

| 상황 | 학생 결과 | 운영진 결과 | 불변조건 |
| --- | --- | --- | --- |
| 파일 업로드 중 | 진행 상태 | 미제출 | 최종 제출 행 없음 |
| 파일 업로드 실패 | 재시도 가능·실패 설명 | 미제출 | 고아 파일 정리 가능 |
| 최종 제출 성공 | 제출 완료·서버 제출 시각 | 제출로 집계 | 제출 기록·파일 참조 동시 확정 |
| 네트워크 응답 유실 | 재조회 후 성공 여부 확인 | 실제 DB 상태를 반영 | 중복 제출·이중 집계 방지 |
| 같은 과제 동시 제출 | 정책상 하나만 확정 | 한 명 1건 | DB UNIQUE + 멱등성 |
| 타 기수·타 학생 ID 호출 | 접근 거부(정보 노출 최소화) | 영향 없음 | 객체별 서버 인가 |
| 마감 바로 전후 제출 | 정책 D4에 따라 허용/차단/지각 | 같은 판정 표시 | 클라이언트 시간 신뢰 금지 |

### 5. 권한·보안·프라이버시

- G1은 **운영진 ADMIN의 과제 관리/제출 확인**과 **해당 학생 본인 제출**에 집중한다. FACULTY의 모든 학생 제출물 조회는 포함하지 않는다.
- Advisor는 수업 운영/출결 담당이며 이 사실만으로 **학생 개인 과제 파일이나 전체 학적에 접근하는 권한을 부여하지 않는다.** 출결 기록·정정 권한도 G1에는 구현하지 않는다. FACULTY에게 출결 권한을 부여하지 않는다.
- 제출 파일은 공개 Blob이 아니라 비공개 저장소 및 인증된 파일 전달 경로로 처리한다. 권한 검사는 UI뿐 아니라 업로드 승인, 최종화, 상세 조회, 파일 다운로드에서 모두 반복한다.
- 서버가 학생 ID, 기수 ID, 파일 소유자, 제출자 정보를 인증 세션·DB 기준으로 결정한다.
- 마감 정책, 파일 보존·삭제, 교수진 검토 범위, 개인정보 파기 기간은 운영 정책 이슈 결정 전까지 **미확정**으로 유지한다.
- 감사 로그에는 actor, resource ID, action, 시각, 결과, 요청 상관 ID를 남기되 이메일·답변 원문·파일 URL·인증 비밀값을 기록하지 않는다.

### 6. 화면 최소 범위

| URL (제안) | 사용자 | G1 기능 |
| --- | --- | --- |
| `/member/assignments` | 해당 기수 학생 | 내 과제 목록·마감·제출 상태 |
| `/member/assignments/[id]` | 해당 학생 | 과제 상세·파일 제출·본인 제출 확인 |
| `/admin/academics/students` | 관리자 | 기수 필터·등록 학생 명부·계정 연결 상태 |
| `/admin/academics/assignments` | 관리자 | 과제 목록·등록·공개·마감 |
| `/admin/academics/assignments/[id]/submissions` | 관리자 | 대상 전원·제출/미제출 현황·허용된 파일 확인 |

기존 `/resources`와 `/mypage` 동작은 유지하고 학사 메뉴를 추가한다. 기존 관리자 CMS를 별도 서비스로 분리하지 않는다.

### 7. G1 통합/E2E 수용 테스트 (필수)

- [ ] 기수 A 학생, 기수 B 학생, `PENDING`, 비로그인, `FACULTY`, `ADMIN` 조합으로 목록·상세·서버 액션·파일 API 권한 검사
- [ ] 해당 기수에 등록돼 있으나 미제출인 학생이 관리자 명단에 표시되고 제출 후 즉시 카운트가 일치
- [ ] 동일 사용자의 같은 기수 이중 등록·같은 과제 이중 제출 및 두 요청 동시 제출 차단
- [ ] 파일 업로드 직후 취소, 업로드 실패, 최종 DB 기록 실패, 성공 응답 유실을 주입해 부분 데이터/중복 없는지 검증
- [ ] 비공개 파일 URL/타 학생 파일 ID 직접 접근 차단; 서버 로그에 파일/PII 유출 없음
- [ ] 학생이 타 기수·비공개·마감 과제에 직접 제출을 시도할 때 서버 정책이 적용되는지 검증
- [ ] 기수 삭제·계정 삭제·과제 비공개 전환 시 보존 대상 기록이 연쇄 삭제되지 않는지 확인

### 8. 기존 이슈와의 경계

기존 보안·무결성·파일 제한과의 중복 구현을 막는다. 권한 기반은 #89·#123, 기존 Blob 정책은 #88·#101, 업로드 한계는 #102·#110, 제출 원자성 참고 사례는 #97, CI 기반은 #103, 기수 삭제 정책은 #109, 기존 모집 접수 정책은 #104를 먼저 확인한다.
