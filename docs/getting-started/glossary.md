# 개발 문서 용어집

HRA 문서에서 자주 쓰는 단어를 작업 맥락과 함께 설명합니다. 모든 용어를 외우기보다 읽다가 막히는 단어를 찾아보세요.

## 코드와 협업

| 용어 | 뜻 | 작업에서 쓰는 예 |
| --- | --- | --- |
| 저장소(repository) | 코드와 변경 이력을 함께 보관하는 공간 | GitHub의 `hra-website` |
| 브랜치(branch) | 변경을 다른 작업과 분리해 진행하는 이름 | `docs/update-guide`에서 문서 수정 |
| 커밋(commit) | 어떤 파일을 왜 바꿨는지 남기는 변경 단위 | 수정한 안내와 이유를 한 번에 기록 |
| PR(Pull Request) | 브랜치의 변경을 다른 사람에게 검토받고 합치자는 요청 | 변경 내용·검증 결과를 설명 |
| 병합(merge) | 검토한 브랜치 변경을 대상 브랜치에 반영 | PR을 `main`에 합치기 |
| 의존성(dependency) | 프로젝트가 설치해 사용하는 외부 패키지 | Next.js, Zod |
| lockfile | 실제 설치할 의존성 버전을 기록한 파일 | `package-lock.json`; `npm ci`가 사용 |
| LTS | 비교적 긴 기간 유지보수를 제공하는 버전 계열 | 개발·CI의 Node 버전을 정할 때 확인 |

## 화면과 서버

| 용어 | 뜻 | HRA에서의 의미 |
| --- | --- | --- |
| 클라이언트(client) | 서버에 작업을 요청하는 프로그램 | 웹 브라우저, 향후 모바일 앱 |
| 서버(server) | 요청에 따라 권한을 확인하고 데이터를 처리하는 프로그램 | Next.js 서버와 기능별 처리 |
| 라우트(route) | 특정 URL을 처리하는 진입점 | 페이지 또는 API 처리 파일 |
| 컴포넌트(component) | 화면을 구성하는 재사용 가능한 부분 | 버튼, 공지 카드, 입력 폼 |
| 서버 액션(Server Action) | 브라우저에서 요청할 수 있는 서버 측 함수 | 폼 저장. 서버에 있어도 권한 검사가 필요 |
| API | 프로그램이 서로 요청·응답하는 약속 | 파일 업로드 허가, 자료 다운로드 |
| 서비스(Application Service) | 한 기능의 업무 규칙과 처리 순서를 묶은 코드 | 과제 공개·제출 확정 |
| 저장소 계층(Repository) | 코드에서 DB 조회·저장을 담당하는 부분 | GitHub 저장소와 문맥을 구분 |
| DTO | 화면이나 API에 전달할 항목만 고른 데이터 형태 | DB의 모든 열 대신 필요한 제목·날짜 전달 |
| OpenAPI | HTTP API의 입력·출력·오류를 기록하는 명세 형식 | 향후 Web/Mobile 공통 계약 |
| 캐시(cache) | 다시 계산하거나 조회하지 않도록 결과를 임시 보관 | 저장 후 목록을 갱신할 때 영향 확인 |

## 데이터와 파일

| 용어 | 뜻 | HRA에서의 의미 |
| --- | --- | --- |
| DB·테이블·행·열 | 데이터를 보관하는 시스템·표·한 건·항목 | 회원 테이블의 회원 한 명과 이름 항목 |
| 스키마(schema) | 어떤 데이터와 관계를 저장할지 정한 구조 | `src/lib/db/schema.ts`와 별도 SQL |
| 마이그레이션(migration) | 기존 DB를 새 구조로 바꾸는 절차 | 열·제약·DB 함수 추가 및 적용 확인 |
| 백필(backfill) | 기존 데이터를 확인해 새 구조의 필요한 값을 채우는 작업 | 승인된 명부를 새 학적 구조와 연결 |
| 카탈로그(catalog) | DB가 보유한 테이블·함수·제약 정보를 조회하는 시스템 정보 | SQL 적용 후 실제 구조 확인 |
| PK·FK | 한 행을 식별하는 기본키·다른 행을 가리키는 외래키 | 제출물이 어느 과제 대상인지 연결 |
| UNIQUE·CHECK | 중복 금지·값의 조건을 강제하는 DB 규칙 | 같은 학생을 같은 기수에 중복 등록하지 않기 |
| 인덱스(index) | 특정 조건의 데이터를 찾기 위한 보조 구조 | 조회 비용과 쓰기 비용을 함께 검토 |
| 트랜잭션·원자성 | 여러 DB 변경을 함께 성공하거나 함께 취소하도록 처리하는 것 | 제출 기록과 파일 연결의 부분 저장 방지 |
| 멱등성(idempotency) | 같은 요청을 재시도해도 추가 결과가 생기지 않는 성질 | 응답이 끊겨도 동일 제출을 중복 생성하지 않기 |
| requestId·멱등성 키 | 요청을 찾는 식별자·같은 작업의 재시도를 구분하는 키 | 기능별 계약을 확인하며, 이름만 같다고 같은 역할로 추정하지 않음 |
| Blob | 이미지·PDF 등 파일 원본을 보관하는 저장소 | 글의 DB 기록과 파일 원본은 별도 |
| private Blob | 공개 URL만으로 파일을 읽을 수 없도록 접근을 제한한 저장소 | 서버가 사용자 권한을 확인한 뒤 전달 |
| 체크섬·SHA-256 | 파일 내용으로 계산하는 비교 값·계산 방식 | 전송·복사 전후 내용이 같은지 확인. 암호화는 아님 |
| 소유권 원장(ledger) | 누가 어떤 업로드를 만들었고 무엇이 참조하는지 추적하는 기록 | 사용 중인 파일과 미완료 파일을 구분 |

## 로그인과 권한

| 용어 | 뜻 | HRA에서의 의미 |
| --- | --- | --- |
| 인증(authentication) | 사용자가 누구인지 확인 | 로그인 |
| 인가(authorization) | 그 사용자가 해당 작업·자료에 접근해도 되는지 확인 | 자기 제출 파일만 열람 |
| 역할(role) | 계정에 부여한 접근 구분 | PENDING, MEMBER, FACULTY, ADMIN |
| OAuth·provider | 외부 계정으로 로그인하는 흐름·그 계정을 제공하는 서비스 | Google·Kakao |
| callback | 외부 인증 후 서비스로 돌아오는 처리 지점 | 개발·Preview·운영 주소를 구분 |
| provider 바인딩 | 외부 서비스의 계정 식별자와 HRA 계정을 연결한 기록 | 이메일이 같다는 이유만으로 계정을 합치지 않음 |
| 세션(session) | 로그인 상태를 확인하기 위한 정보 | 쿠키와 서버의 현재 계정 상태를 함께 확인 |
| sessionVersion | 기존 로그인 상태를 무효화하기 위해 비교하는 계정 버전 | 역할 변경·세션 폐기 시 사용 |
| rate limit | 정해진 시간 동안 요청 횟수 등을 제한하는 규칙 | 로그인·업로드 등의 요청 보호 |
| fail-closed | 설정이나 권한 확인이 불충분하면 접근을 거부하는 동작 | 준비되지 않은 학사 기능의 접근 거부 |

## 환경과 검증

| 용어 | 뜻 | 작업에서 확인할 점 |
| --- | --- | --- |
| 환경변수 | 실행 환경별 설정값 | 주소와 기능 설정뿐 아니라 비밀값도 포함 |
| Development·Preview·Production | 내 개발 환경·PR 확인 환경·실제 이용자 환경 | DB·Blob·OAuth를 구분 |
| staging | 별도로 유지하는 운영 전 검수 환경 | HRA는 필요가 생겼을 때 도입하는 목표 |
| 빌드(build) | 배포해 실행할 앱을 만드는 작업 | 성공해도 운영 DB 준비를 보장하지 않음 |
| 배포(deploy) | 실행할 앱과 설정을 특정 환경에 올리는 작업 | 실제 URL의 응답을 별도 확인 |
| 릴리스(release) | 사용자에게 전달할 변경을 버전과 기록으로 묶는 작업 | 배포·GitHub Release·앱스토어 출시를 구분 |
| CI | 변경 때 자동으로 정해진 검사를 실행하는 과정 | 실행한 job과 테스트 범위를 확인 |
| 단위·통합·E2E 테스트 | 작은 함수·연결된 구성요소·실제 사용자 흐름의 검사 | 서로 다른 범위의 증거 |
| smoke 검사 | 핵심 경로가 기본적으로 동작하는지 빠르게 확인 | 모든 기능을 검사했다는 뜻은 아님 |
| fixture | 테스트를 위해 준비한 예시 데이터·파일 | 운영 개인정보 대신 합성 데이터를 사용 |
| gate | 다음 단계로 넘어가기 위한 조건 | 검사 통과, 운영 승인, 명시적 기능 설정 |
| dry-run | 실제 변경 없이 예정 작업을 확인하는 실행 | 해당 스크립트가 정말 읽기 전용인지 확인 |
| rollback·forward-fix | 이전 상태로 되돌리기·현재 상태에서 추가 수정으로 복구하기 | 앱과 DB의 복구 방법은 다를 수 있음 |
| cron | 정해진 일정에 따라 요청·작업을 실행하는 설정 | 등록, 인증, 실제 삭제 허용을 각각 확인 |

## 학사 문서

| 용어 | 뜻 | HRA에서의 의미 |
| --- | --- | --- |
| 학적(enrollment) | 특정 학생이 특정 기수에 등록한 관계 | 계정의 역할이나 `users.cohortId`와 동일하지 않음 |
| 대상 스냅샷 | 정해진 시점에 대상 명단을 고정한 기록 | 과제를 처음 공개할 때의 대상 학생 |
| G1·G2·G3 | 학사 기능을 나눈 단계 이름 | 명부·제출 / 출결 / 피드백·수료 |
| 최종화(finalize) | 업로드한 파일을 검증하고 제출 사실을 확정하는 단계 | 업로드 성공과 최종 제출 성공을 구분 |
| 감사 로그(audit log) | 누가 언제 어떤 변경을 했는지 추적하는 기록 | 민감한 본문·토큰·파일 URL을 그대로 기록하지 않음 |

권한과 학사 정책의 세부 기준은 [학사 로드맵](../ACADEMIC-MANAGEMENT-ROADMAP.md)과 각 기능 문서가 정합니다. 이 용어집은 해당 정책을 새로 승인하거나 기능을 활성화하지 않습니다.
