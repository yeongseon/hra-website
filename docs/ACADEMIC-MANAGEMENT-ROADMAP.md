# HRA 학사관리 시스템 전환 계획 (제안서)

> 상태: **설계 초안 / 구현되지 않은 기능 포함** · 기준: 2026-10-13, `main` `bfa49dc`.
> 이 문서는 기존 HRA 사이트를 가벼운 학사관리(SIS + LMS)로 확장하기 위한 방향과 구현 순서를 정의한다. **운영 정책의 최종 확정이나 기능 출시를 의미하지 않는다.**

## 1. 목표 및 성공 기준

- HRA의 기수별 1년 교육을 **학생 개인** 중심으로 기록한다. 모집 → 등록 → 수업 → 과제 → 출결 → 수료 흐름을 단계적으로 연결한다.
- 기존 Next.js 16 / NextAuth / Neon PostgreSQL / Drizzle / Vercel Blob 구조를 우선 재사용한다. 별도 ERP, 마이크로서비스, 학점·수강신청 시스템을 도입하지 않는다.
- 첫 번째 운영 가능한 산출물(MVP)은 **기수별 대상 학생 전원이 표시되는 과제 제출 현황**이다. 미제출자는 제출 데이터가 없어도 명단에 나타나야 한다.
- 공개 사이트·홍보 콘텐츠 관리·현재 자료실의 동작은 유지한다. `weekly_texts`와 `class_logs`는 공동 학습 콘텐츠이며 학생별 제출물로 재해석하지 않는다.
- 승인된 사용자라도 **자기 학적에 해당하는 과제와 자기 제출물만** 조회한다. 파일 주소만으로 비공개 제출물에 접근할 수 없어야 한다.
- 오류·취소·동시 제출·네트워크 재시도 상황에서도 동일 과제의 제출 상태가 일관되며, 과거 기록이 예기치 않게 삭제되지 않아야 한다.

### 실제 수업 운영 주체 (2026-10-13 확인)

- **교수(FACULTY)는 출결 업무를 담당하지 않는다.** 교수의 수업·학습 내용 담당과 과제 피드백 권한은 별도로 검토한다.
- 각 수업의 출결은 해당 기수에 배정된 운영 인력이 담당한다. 최종 정정·승인 절차는 #143에서 확정한다.
- 수업 운영 인력은 **어드바이저 1명과 조교 2명**이다. **세 사람이 돌아가며 출결을 체크한다.** 따라서 출결 입력 권한은 어드바이저뿐 아니라 조교에게도 필요하다.
- 어드바이저와 조교는 **기수마다 다른 사람**이며, 한 기수 안에서는 수업마다 바뀌지 않는 **고정 배정**이다. 다만 **조교는 학기 중에 바뀔 수 있고 향후 역할도 바뀔 수 있으므로**, 배정은 기수·역할(어드바이저/조교)·기간(시작·종료)을 함께 기록해 변경 이력을 남기고, 교체된 사람의 권한은 종료 시점에 회수한다.
- 이들을 **관리하는 담당자가 따로 있으며, 홈페이지 관리자(`ADMIN`)와 다른 사람이다. `ADMIN` 은 홈페이지만 관리한다.** 따라서 `ADMIN` 이라는 이유만으로 출결·학사 운영 권한을 주지 않고, 운영 인력 배정·교체와 출결 감독은 별도의 학사 운영 관리 권한으로 분리한다. 이 권한의 구체적 범위(출결 최종 승인, 학적·과제 관리 포함 여부)는 #143에서 확정한다.
- 어드바이저·조교는 최초에는 특정 기수에 **기간을 정해 배정되는 업무상 역할**로 취급한다. 현재 전역 `users.role`에 해당 역할이 없으며, 승인 없이 역할 enum을 확장하거나 교수의 `facultyId`를 운영자로 재사용하지 않는다.
- 학사 운영 관리 담당자의 감독·예외 처리와 운영 인력 부재·교체·대리 입력 규칙은 #143에서 확정한다. 관련 구현: #165.

## 4. 사용자 여정 및 기능 단위

### 운영진

1. 기존 모집/지원서에서 합격을 관리한다. 합격만으로 계정을 자동 승격하거나 이메일이 같다는 이유로 기존 계정에 학적을 자동 부여하지 않는다.
2. 신원과 참여 의사가 확인된 대상자를 특정 기수의 학적/학생명부에 등록한다. 같은 기수·동일 학생의 중복 등록을 차단한다.
3. 해당 기수의 과제를 생성·수정·공개하고 선택적으로 기존 수업일/세션에 연결한다.
4. **학적 명부 LEFT JOIN 제출** 방식으로 제출·미제출·지각(정책 확정 시)을 구분한다.
5. 학생별 파일 열람은 객체 수준 권한을 재검증하고, 상태 변경·삭제·내보내기는 감사 기록을 남긴다.

### 학생

1. 로그인 후 본인의 활성 학적을 조회한다. 소속 기수가 없거나 승인 대기라면 분명한 안내를 표시한다.
2. `/member/assignments`에서 **자신에게 공개된** 과제와 마감·제출 여부를 확인한다.
3. 허용된 형식의 파일을 안전하게 업로드하고 최종 제출을 확정한다. 업로드는 제출 완료와 동의어가 아니다.
4. 본인의 제출물과 시각만 확인한다. 타인의 제출물 URL/ID 추측·직접 호출이 실패해야 한다.

### 수업 운영 인력(어드바이저·조교) — G2 담당

- 기수별·역할별 기간 배정으로 어드바이저 1명과 조교 2명의 출결 입력을 관리한다. 정정·최종 승인 범위는 #143에서 결정한다.
- 로그인 계정과 해당 수업일의 기수에 유효한 운영 인력 배정을 함께 검증해야 출결 입력에 접근할 수 있다. 단지 MEMBER·FACULTY·ADMIN이라는 이유로 출결 권한을 주지 않는다.
- 다른 기수의 출결과 학적 정보는 열람하지 않는다. 본인 배정 종료 이후 즉시 권한을 상실해야 한다.

### 교수진 — 수업 내용 및 승인된 과제 검토

- 본인 계정에 연결되고 **담당자로 지정된** 수업/과제만 검토한다.
- `FACULTY` 역할만으로 모든 기수의 개인 제출물을 열람시키지 않는다.
- 기존 홍보용 `faculty` 프로필과 로그인 `users`는 현재 별도이며, 검증된 연결이 필요하다.
- **교수는 출결 담당자가 아니다.** 교수 역할·수업의 `facultyId`로 출결 열람·입력·정정 권한을 부여해서는 안 된다. 교수의 과제 검토는 별도 정책에 따른다.

## 6. 데이터·보존·마이그레이션 원칙

- 학적의 정본은 신규 `cohort_enrollments`로 제안한다. 기존 `users.cohortId`는 **전환 기간에만 호환 필드**로 유지하고 당장 삭제하거나 자동 덮어쓰지 않는다.
- 과제와 제출 파일은 명시적인 소유권/참조 관계로 기록한다. 제출 파일에 `access: public`을 사용하지 않는다.
- 운영 기록의 변경은 누가/언제/무엇을/왜 바꾸었는지 감사할 수 있어야 한다. 감사 로그에는 민감한 자유서술 본문·파일 URL 전체를 적지 않는다.
- 기수·학생 계정의 일반 삭제로 제출/출결 기록이 묵시적으로 연쇄 삭제되지 않도록 FK 정책을 확인한다. 합법적인 개인정보 삭제 요청은 별도 명시적 절차로 구현한다.
- 백필은 **읽기 전용 점검 → dry-run → 격리 DB 마이그레이션 검증 → 운영 승인 → 적용/검증** 단계로 처리한다. 계정 이메일 일치만으로 지원서나 과거 학적을 자동 연결하지 않는다.
- `Asia/Seoul` 달력 날짜와 정확한 시각(UTC instant)을 혼동하지 않는다. 과제 마감 시각·지각 판정은 명시적인 KST 정책이 먼저 필요하다.
- 기존 Drizzle 스키마와 DB 마이그레이션 이력이 일치하는지 검증하며, 운영 DB에 `drizzle-kit push`만을 무검토 실행하지 않는다.

상세 스키마·인덱스·경합 조건은 [학사 데이터 모델](ACADEMIC-DATA-MODEL.md), G1 과제 범위는 [과제 제출 1차 범위](ASSIGNMENT-SUBMISSION-SCOPE.md)에 정의한다.

## 8. 완료 정의와 추적

- 신규 서버 기능은 검증된 입력 스키마, 역할+기수+대상 객체 권한 검증, 유일/외래키 제약, 실패 후 재시도와 감사 경로를 갖춰야 한다.
- DB/Blob 쓰기는 성공/실패/응답 유실/동시 실행에서 불변조건을 테스트한다.
- 격리된 테스트 DB·테스트 Blob만 사용하고 실제 학생 자료와 실제 URL을 테스트/이슈에 올리지 않는다.
- CI는 lint/typecheck/unit/build를 유지하고 G1 핵심 흐름에 대해 통합·E2E 게이트를 추가한다.
- 과제 제출 E2E는 **기수 A 학생, 기수 B 학생, 승인 대기, 교수진, 관리자**, 업로드 실패, 중복 제출, 마감 경계, 비공개 파일 다운로드를 포함한다.
- G2 출결 E2E에는 **해당 기수에 배정된 어드바이저·조교 / 배정이 종료된 인력 / 다른 기수 배정자 / FACULTY / 학생 / ADMIN / PENDING**을 포함한다. `FACULTY`·`ADMIN` 역할만으로 출결 입력을 허용하지 않는다.
- 운영진에게 보여 줄 상태 지표(기수별 전체 대상/제출/미제출/장애)를 명확히 정의한다.

기존 이슈(중복 생성하지 않음): #88, #89, #91, #93, #95, #97, #100, #101, #102, #103, #104, #109, #110, #121, #123, #125.
새 구현 작업은 기능 단위로 GitHub 이슈에 분리해 기록하며, 이 문서와 이슈의 완료 조건을 동일하게 관리한다.
