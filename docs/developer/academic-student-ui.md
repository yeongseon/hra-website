# 학생 과제 목록·제출 UI

학생의 과제 화면과 제출 실패 안내를 개발·검수할 때 읽는다. 사용자는 과제를 확인하고 파일을 고르지만, 화면은 전송·서버 검증·DB 제출 확정·결과 재조회를 각각 구분해야 한다. **업로드 100%**는 파일 전송이 끝났다는 표시이며, 서버가 최종 제출을 확인한 뒤에 완료 화면을 보여준다.

목록·상세·제출 화면은 구현되어 있다. 기능을 사용할 수 있는지는 본인 학적·공개 대상·운영 설정을 따로 확인한다. 아래 화면 흐름부터 읽고, 데이터 변경은 [본인 조회 계약](academic-student-queries.md), 저장·재시도 변경은 [최종화 계약](academic-submission-finalization.md), 전체 연결 확인은 [G1 품질 게이트](academic-g1-quality-gate.md)를 따른다.

#154는 실제 학생 세션과 G1 과제 서버 계약을 사용하는 목록·상세·파일 제출 화면이다. 운영 설정을 자동으로 켜거나 기존 공동 자료실·학적·파일 정책을 변경하지 않는다.

## 화면과 조회

`/member/assignments`와 `/member/assignments/[id]`는 동적 서버 페이지다. 부모 레이아웃과 별개로 매 요청 `requireAcademicStudent()`와 #150 본인 대상 조인을 실행한다. ADMIN/FACULTY를 학생으로 취급하지 않으며 승인 대기는 기존 `/pending` 경계를 따른다. MEMBER 마이페이지에는 기능이 활성화된 경우에만 내 과제 링크를 추가한다. 지정 학사 승인자의 관리 링크는 별도 #146/#155 작업을 보존한다.

`getMyAcademicUiContext()`는 현재 MEMBER DB 역할도 확인하고 본인 활성 학적 여부와 DB 현재 시각만 반환한다. 학적이 없는 MEMBER에게는 계정 연결·기수 등록 문의를, 유효 학적이 있지만 공개 대상이 없는 경우에는 아직 과제가 없음을 안내한다. 상세의 잘못된 UUID·비공개·미래 공개·다른 학생/기수는 #150의 동일한 404 계약을 사용한다.

마감 표시와 새 전송 가능 여부는 DB가 반환한 현재 시각과 과제 상태로 판단한다. 브라우저 `Date.now()`로 인가하지 않는다. 화면을 오래 열어둔 사이 마감이 지났더라도 최종 DB 함수 #148/#152가 제출을 차단한다. 날짜 표시는 기존 Asia/Seoul 공통 헬퍼를 사용한다. 안내 본문은 React 텍스트로 표시하여 HTML을 실행하지 않는다.

#150의 현재 본인 제출 DTO에는 `submissionId`가 포함된다. 실제 자기 제출 LEFT JOIN에서만 선택하며 타인 ID·파일 URL·저장 키는 반환하지 않는다. 완료 다운로드는 `/api/academic/submissions/[submissionId]/file/[fileId]`로만 연결한다.

## 업로드·실패·완료 상태

1. 기존 #151의 `assignmentUploadInput`으로 비어 있지 않은 PDF 한 개·50MiB 이하·이름/MIME를 확인한다. 실제 내용·크기·소유권은 서버가 다시 검증한다.
2. `uploadAssignmentFile()`로 실제 비공개 직접 업로드를 실행하고 진행률을 표시한다. 발급 직후 `onIntent`가 의도 UUID를 전달하여 PUT 성공 응답 유실에도 복구할 수 있게 한다.
3. #152의 실제 `finalizeAssignmentSubmission()` 서버 액션으로 객체 검증·원자 최종화를 요청한다. UI가 임의 파일 URL·학생/기수/계정을 전달하지 않는다.
4. 액션이 성공해도 즉시 완료로 표시하지 않는다. `refreshMyAssignment()` 서버 액션이 #150을 재조회하여 본인 최종 `submissionId`와 제출 시각을 확인한 뒤 완료 화면을 표시한다.

요청 UUID와 최종 멱등 키는 한 시도 동안 유지하고 업로드 의도도 함께 기억한다. 탭 저장소에는 이 UUID들만 대상 ID별로 저장하며 파일·파일명·이메일·토큰은 저장하지 않는다. 저장소가 막혀도 현재 화면의 메모리에서 재시도할 수 있다. 저장 실패는 고정 한국어 안내로 표시하여 새로고침 복구가 보장되지 않음을 알린다. 내부 예외 문구는 노출하지 않는다.

전송/최종화 오류 시 선택 파일과 요청을 지우지 않는다. 의도가 있으면 기본 재시도는 같은 최종화 요청의 결과 복구를 실행한다. 객체 없는 전송 실패·요청 제한·파일 내용 거부·만료 등 원인에 관계없이 «업로드 취소 후 다시 시작»을 제공한다. 이 경로는 현재 본인 최종 결과를 먼저 재조회하고, 미완료일 때만 실제 #151 DELETE 취소를 요청한다. 명시적인 CANCELLED 성공 후에만 새 요청 UUID·최종 멱등 키로 전환하며 선택한 File은 유지하고 다른 파일 선택도 허용한다. 이전 의도로 직접 파일을 다시 쓰지 않는다. 취소 실패·응답 유실 시 현재 최종 결과를 다시 조회하고, 이미 확정됐다면 원본 완료/파일을 표시한다. 여전히 미완료라면 기존 의도·키·파일을 유지하여 안전한 재취소를 허용한다. 앱에서 Blob을 직접 삭제하지 않는다. 완료 후에는 교체/재제출 UI를 제공하지 않는다. 새로고침해도 서버의 동일한 최종 ID·시각·파일을 표시하며 저장한 의도가 있으면 파일 재선택 없이 기존 요청을 복구할 수 있다.

상태는 파일 선택·전송 중·검증/최종화 중·서버 결과 확인 중·실패·완료로 구분한다. 업로드 진행률 100%만으로 완료를 표시하지 않는다. 중복 클릭은 즉시 잠금으로 막고, 완료 후 제목에 초점을 옮긴다. 파일 라벨·도움말·`aria-live` 상태·진행률·줄바꿈과 작은 화면의 버튼 배치를 제공한다. SDK/DB 오류 원문이나 저장 키를 화면/로그로 복사하지 않는다.

## 검증

```sh
HRA_TEST_PG_BIN=/opt/homebrew/opt/postgresql@18/bin npx vitest run tests/unit/academic-student-query-*.test.ts tests/unit/academic-student-ui.test.ts tests/unit/academic-student-replacement-postgres.test.ts
HRA_TEST_PG_BIN=/opt/homebrew/opt/postgresql@18/bin node scripts/verify-academic-student-ui.mjs
```

단위 테스트는 실제 폼의 업로드/최종화 실패 보존·PUT 응답 유실·동일 키 복구·서버 재조회 전 완료 금지·PDF 오류·새로고침 복구·안전한 취소/교체·취소 응답 유실·현재 탭 파일 보존·저장소 실패 안내를 검증한다. 별도 실제 PostgreSQL 두 연결은 취소 우선/최종화 우선 경합을 각각 잠금 대기로 확인하고 확정 파일 보존 또는 새 의도 허용을 검증한다. 격리 PostgreSQL은 실제 서비스 SQL로 본인 제출 ID 비노출 경계와 학적/DB시각 helper를 확인한다. QA 실행기는 운영 환경 파일을 읽지 않고 합성 credentials·격리 PostgreSQL·실제 Next/Playwright로 목록/서버 확정 결과/새로고침/모바일 파일 오류를 실행한다. 기본 QA는 외부 Blob 업로드를 실행하지 않는다.

실제 공급자 QA는 승인된 private 저장소를 서버 환경에만 주입하고 `HRA_ACADEMIC_UI_PROVIDER_QA=true`로 같은 실행기를 실행한다. 실행기가 새로운 본인 과제를 만들고 Playwright에 해당 UUID만 전달한다. 브라우저에는 저장소 쓰기 비밀키를 전달하지 않는다. 비민감 `resourceQaPdfBytes()`를 실제 SDK로 전송하고 최종화 응답만 유실시킨 뒤 같은 키 복구와 새로고침 결과를 확인한다. 추가 공급자 사례는 실제 의도/토큰 뒤 PUT 전송 실패를 주입하여 파일 보존과 안전한 취소를 확인하고, 위장 PDF 서버 거부 뒤 다시 취소한 다음 정상 PDF를 새 의도로 확정한다. 발급 요청과 토큰·검증 합계의 독립적인 대상 4회/사용자 6회/60초 제한을 유지한다. PUT 실패 뒤 취소·새 전송은 같은 창에서 복구하고, 외부 작업 예산을 모두 쓴 경우에는 안내된 대기 시간을 따른다. 기본 실행에서 공급자 사례를 생략한 결과를 실제 공급자 업로드 성공으로 보고하지 않는다.

실제 공급자 모드는 발급 응답을 브라우저에 넘기기 전에 저장 키·만료 시각을 별도 0600 QA 원장에 기록한다. 공개 로그에는 원장 파일 위치만 출력하고 키/URL은 출력하지 않는다. 이 실행기가 발급한 객체의 정리는 승인된 운영자의 별도 QA 원장 절차로 수행한다. 앱의 보존 정책을 우회하는 자동 삭제는 추가하지 않는다. #158의 격리 CI에서는 외부 저장소 전송 경계만 대체하여 전체 업로드 플로우도 별도로 실행한다.

### 2026-10-16 검증 기록

아래 숫자와 실행 조건은 당시 기록이다. 이번 문서 정비에서 같은 검증을 재실행한 결과가 아니며, 이후 확장된 사례의 통과를 이전 기록으로 대신하지 않는다.

- 최초 대상 단위/실제 PostgreSQL: 46건 통과. 이후 복구 보강의 새 검증 결과는 아래에 별도 기록한다.
- 공급자 없는 기본 실제 앱 QA: 3건 통과, 실제 공급자 사례 1건은 명시 생략.
- 최초 승인된 실제 private 공급자를 사용한 동일 실행기: 4건 모두 통과. 실제 SDK 업로드 → 최종화 응답 유실 → 같은 요청 복구 → 새로고침의 동일 결과까지 확인했다. 서버·격리 DB는 종료했으며 공급자 객체는 별도 0600 QA 원장으로 추적한다.

### 취소·교체 보강 검증

- 대상 조회·폼·실제 PostgreSQL 전체 55건 통과. 실제 폼 회귀 14건 통과. INVALID_FILE·전송 실패 후 안전 취소, 두 취소 경합 결과의 UI 복구, 취소 응답 유실 시 기존 키/파일 보존, sessionStorage 실패 안내를 포함한다.
- 실제 격리 PostgreSQL 취소/최종화 양방향 경합 및 새 의도 제출 3건 통과. 공급자 없는 실제 앱 QA는 3건 통과, 공급자 2건 명시 생략.
- 최신 #151 3인자 취소 사본 동기화 후에도 55건 재통과, ESLint와 `npm run build` exit 0. 빌드의 TypeScript 검사도 완료했다.
- 확장 공급자 사례는 준비했으며 실제 공급자 5건 재실행 결과는 상위 통합 검증에서 별도 확인한다. 기존 4건 성공을 이 새 사례의 통과로 간주하지 않는다.
