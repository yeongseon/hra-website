# 개인 과제 제출 최종화

파일을 올린 뒤 언제 제출 완료로 확정할지 수정하는 개발자가 읽습니다. **최종화**는 검증된 파일과 제출 기록을 DB에 함께 확정하는 단계입니다. **멱등성**은 같은 제출 키로 다시 요청해도 중복 제출을 만들지 않고 기존 결과를 돌려주는 성질입니다. 통신이 끊겨 성공 여부를 모를 때 이 성질로 복구합니다.

최종화 서비스·액션·SQL 함수는 구현되어 있습니다. [업로드 검증](academic-assignment-uploads.md) → 이 문서의 확정·복구 절차 → [파일 다운로드](academic-submission-files.md) 순서로 읽습니다. 화면은 [학생 UI](academic-student-ui.md), 연결 검증은 [G1 품질 게이트](academic-g1-quality-gate.md)를 따르며 운영 활성화는 아래 승인 조건을 별도로 확인합니다.

#152는 실제 파일 업로드 검증과 DB 최종 제출을 연결합니다. 파일 업로드 성공만으로 제출 완료를 반환하지 않습니다.
입력은 `assignmentId`, `uploadIntentId`, 영속 `submissionKey` UUID 세 개뿐입니다.
학생·계정·기수·저장 키·URL·파일 메타는 클라이언트에서 받지 않습니다.

## 선행 적용과 운영 경계

격리 DB에서 #144 학생·학적 → #147 과제·대상 → 보강된 #148 제출 → #151 업로드 승인 원장 순서로 검증한 뒤
`scripts/migrate-academic-submission-finalization.sql`을 적용합니다. 같은 SQL 재실행도 지원합니다.
새 테이블이나 Drizzle 모델은 추가하지 않고 `complete_academic_assignment_submission` wrapper만 추가합니다.
함수는 SECURITY INVOKER이며 PUBLIC 실행 권한을 회수합니다. 앱 DB 역할의 필요한 함수·테이블 권한은 별도 운영 절차로 부여합니다.

실제 MEMBER 세션·현재 본인 학적·최초 공개 대상이 일치해야 합니다.
`ACADEMIC_ENABLED=true`가 아니면 #150 인가가 DB 접근 전에 차단합니다.
새 제출에는 `ACADEMIC_ENROLLMENT_WRITES_ENABLED=true`와 #151의 `ACADEMIC_UPLOADS_ENABLED=true`가 필요합니다.
보존 정책 #142와 운영 승인이 완료되기 전에는 운영 기능을 활성화하지 않습니다.

## 처리 순서

1. 공개 입력 UUID를 검증하고 실제 세션으로 `requireAssignmentTarget`을 호출합니다.
2. wrapper를 복구 조회 모드로 실행합니다. DB가 현재 계정·학적을 잠금·재검증하고 동일 키 성공을 먼저 찾습니다.
3. 이미 완료한 동일 대상·계정·의도·키라면 저장된 제출 ID와 완료 시각을 반환합니다.
   이 경로는 마감·종료·의도 만료·CONSUMED와 업로드 저장소 장애에 영향받지 않습니다.
   새 쓰기·업로드를 중단한 경우에도 이미 완료된 성공 복구는 허용합니다.
4. 성공 기록이 없을 때만 #151 실제 `verifyAssignmentUploadIntent({assignmentId, uploadIntentId})`를 호출합니다.
   검증기는 Private Blob의 존재·정확한 저장 경로·크기·MIME·PDF 시그니처·체크섬·버전을 확인하고 VERIFIED 메타를 영속화합니다.
5. 외부 객체를 읽는 사이 세션·본인 대상이 바뀌었는지 다시 인가합니다.
6. 같은 wrapper를 최종화 모드로 실행합니다. 현재 권한·만료·마감·검증 상태를 다시 검사하고
   #148 `finalize_academic_assignment_submission`으로 제출·파일·CONSUMED를 원자 확정합니다.
   #151 취소·정리 선점 원장도 INSERT 트리거가 다시 확인합니다.

wrapper 잠금 순서는 #148과 같은 대상 → 계정 → 학생/학적 → 과제 → 의도입니다.
공통 owner 함수와 wrapper 모두 현재 MEMBER, 본인 연결, ENROLLED, 종료 없음, 미래가 아닌 등록 시각을 확인합니다.
권한 철회가 먼저 커밋되면 새 제출과 동일 키 복구 모두 차단합니다. 기존 최종 기록은 보존합니다.
다른 키의 동시 제출은 대상 잠금·UNIQUE에 따라 하나만 확정됩니다.
같은 키라도 다른 대상·계정·의도로 재사용하면 기존 결과를 노출하지 않고 충돌을 반환합니다.

## 결과와 실패 복구

성공 결과는 과제·제출 ID, DB 완료 시각, 재시도 여부, 본인 파일 ID·이름·MIME·크기만 포함합니다.
저장 키·URL·체크섬·사용자/학적 ID는 반환하지 않습니다.
학생 과제 목록·상세와 관리 목록·제출 현황 경로를 갱신합니다.
마감과 완료 시각은 클라이언트가 아니라 DB 시각으로 판단합니다.

파일 검증 성공 뒤 DB 실패, 커밋 전 요청 중단, 커밋 후 HTTP 응답 유실에서는 같은 submissionKey로 재시도합니다.
파일 행 실패는 제출·파일·소비 상태 전체를 롤백합니다. 커밋 후 응답 유실은 기존 완료 ID·시각으로 복구합니다.
이 액션은 실패하거나 경쟁에서 졌다는 이유로 Blob을 삭제하지 않습니다.
같은 객체가 승자 제출에서 사용됐거나 커밋 여부가 불명확할 수 있습니다.
만료 객체 정리는 #151 별도 수명주기에서 DB 참조·소비·정리 선점을 확인한 뒤 수행합니다.

예상 오류는 고정 한국어 코드·상태로 전달합니다. 예상외 오류도 고정 메시지와 검증된 제출 키만 로깅합니다.
Drizzle 원본 오류의 SQL·params·파일명·연락처·본문·URL은 로그 정제기에 전달하지 않습니다.
학생·관리 조회는 #150과 같은 최종 제출 행과 파일 행을 사용하므로 완료 시각이 일치합니다.
