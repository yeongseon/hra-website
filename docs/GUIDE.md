# HRA 웹사이트 개발 가이드

이 문서는 HRA에서 **무엇을 어디서 바꾸고, 어떻게 확인한 뒤 제출하는지** 찾는 안내서입니다. 프로그래밍 전공 지식 없이도 작은 작업부터 따라갈 수 있도록 현재 코드 구조와 운영 작업을 구분했습니다.

처음 실행한다면 [사전 준비](getting-started/prerequisites.md) → [프로젝트 설정](getting-started/clone-and-setup.md) → [첫 실행](getting-started/first-run.md) 순서로 읽습니다. 용어가 낯설면 [기초 용어집](getting-started/glossary.md)을 참고합니다.

## 1. 하려는 일에 맞는 시작점 찾기

| 하려는 일 | 먼저 볼 곳 | 완료 확인 |
| --- | --- | --- |
| 내 컴퓨터에서 사이트 실행 | [시작하기](getting-started/clone-and-setup.md) | 개발 서버와 필요한 DB·로그인 연결을 확인합니다. |
| 문구·화면·기능 코드 수정 | [협업 절차](contributing/workflow.md), [코드 규칙](contributing/conventions.md) | 변경 화면, 검사 결과, PR 리뷰를 확인합니다. |
| 공지·교수진·갤러리 등 운영 콘텐츠 수정 | [관리자 안내](ADMIN-GUIDE.md)와 홈페이지의 관리자 화면 | 올바른 환경에서 저장했는지, 공개 화면에 의도대로 보이는지 확인합니다. |
| DB 구조 변경 | [데이터베이스 변경 절차](developer/database-change-procedure.md) | 적용 대상·백업·추가 SQL·복구와 사후 조회를 확인합니다. |
| 카카오 로그인 연결 | [카카오 로그인 설정](KAKAO-LOGIN-SETUP.md) | 버튼 표시뿐 아니라 로그인 왕복과 기존 계정 연결을 확인합니다. |
| 사이트 배포 | [배포 안내](DEPLOYMENT.md), [빌드·배포 검사](contributing/build-and-deploy-safety.md) | 배포된 주소에서 변경 기능과 권한을 확인합니다. |

코드 변경은 브랜치와 PR로 검토합니다. 관리자 화면에서 저장하는 콘텐츠는 연결된 DB에 직접 반영되므로, 개발 연습은 개발 환경에서 합니다.

## 2. 현재 폴더와 데이터 저장 위치

**컴포넌트(component)**는 버튼·머리글·목록처럼 화면을 구성하는 코드 단위입니다. **서버 액션(Server Action)**은 화면에서 호출할 수 있는 서버 함수로, 로그인 사용자 확인과 입력 검증이 필요합니다.

| 현재 경로 | 들어 있는 것 |
| --- | --- |
| `src/app` | 페이지, 화면 묶음의 레이아웃, API 요청 처리 |
| `src/app/(public)` | 홈·소개·교수진·모집 등 공개 페이지 |
| `src/app/(auth)` | 로그인 관련 화면 |
| `src/app/(admin)` | 관리자 화면 |
| `src/app/(member)` | 회원 화면 |
| `src/components` | 여러 화면에서 쓰는 UI |
| `src/features` | 공지·회원·지원서 등 기능별 조회와 변경 코드 |
| `src/lib` | DB 연결, 인증, 업로드 등 공통 코드 |
| `scripts` | 관리자 초기 생성, DB 변경, 검사 등 관리 스크립트. 저장소 최상위에 있습니다. |
| `public` | 코드와 함께 배포하는 정적 이미지 등의 파일 |
| `docs` | 개발·운영·협업 문서 |

`(public)`처럼 괄호로 둘러싼 폴더는 코드를 묶기 위한 이름입니다. `src/app/(public)/about/page.tsx`의 주소는 `/about`입니다.

현재 공지·갤러리·회원·지원서 등의 데이터는 **PostgreSQL 데이터베이스**를 사용하고, 업로드한 파일은 **Vercel Blob**에 저장합니다. `content/`의 과거 파일이 남아 있어도 새 공지나 갤러리를 그 폴더에 추가하는 절차로 안내하지 않습니다. 개발 문서 파일과 운영 콘텐츠의 저장 위치를 혼동하지 않는 것이 중요합니다.

Web·Android·iOS와 공통 업무 코드를 **한 저장소 안에서** 앱·모듈별로 관리하는 **모노레포(monorepo)** 전환은 [플랫폼 아키텍처](developer/platform-architecture.md)의 목표입니다. `apps/web`, `apps/mobile`, `server/modules`는 목표 경로이며 현재 모든 기능이 그곳으로 옮겨진 상태는 아닙니다.

## 3. 코드를 바꾸는 기본 순서

1. [열린 이슈](https://github.com/yeongseon/hra-website/issues)에서 같은 작업이 있는지 확인하고 범위를 정합니다.
2. 진행 중인 변경이 없는지 확인한 뒤 최신 `main`에서 작업 브랜치를 만듭니다.
3. 필요한 파일만 수정하고 `git diff`로 변경 내용을 읽습니다.
4. 화면과 관련 검사를 확인합니다.
5. 필요한 파일을 커밋해 작업 브랜치에 올리고 PR을 만듭니다.
6. CI와 리뷰, 배포 후 확인 등 완료 조건을 충족한 뒤 병합·완료 처리합니다.

**커밋(commit)**은 한 묶음의 변경 기록이고, **PR(Pull Request)**은 그 변경을 팀에 검토받는 요청입니다. **CI(Continuous Integration)**는 GitHub에서 자동으로 실행하는 검사입니다.

작업 전 `git status --short`에 기존 수정이 보이면 먼저 해당 작업을 정리합니다. 다음은 문서 작업의 예시입니다.

```bash
git status --short
git switch main
git pull --ff-only origin main
git switch -c docs/update-guide
```

수정한 뒤에는 파일을 골라 기록합니다.

```bash
git diff
git add docs/GUIDE.md
git diff --cached
git commit -m "docs: 개발 가이드 설명 수정"
git push -u origin docs/update-guide
```

브랜치를 올린 다음 GitHub에서 PR을 만듭니다. `main`에 직접 푸시하는 방식은 사용하지 않습니다. 상세한 이슈·PR 형식과 `Closes`/`Refs` 구분은 [협업 절차](contributing/workflow.md)를 따릅니다.

충돌이 나면 양쪽 변경의 목적을 먼저 확인합니다. 어느 쪽을 남길지 이해하지 못한 채 한쪽을 통째로 선택하거나 변경을 강제로 덮어쓰지 않습니다. 관련 작업자와 결정한 결과를 다시 검사합니다.

## 4. 작은 화면 변경부터 시작하기

### 문구와 메뉴

화면의 글자가 파일에 직접 적혀 있으면 해당 컴포넌트를 수정합니다. 관리자 화면에서 편집하는 제목·본문·이미지라면 DB에 저장되는 콘텐츠이므로 관리자 화면을 사용합니다. 검색할 때는 실제 보이는 짧은 문구를 기준으로 찾으면 위치를 좁힐 수 있습니다.

- 상단 메뉴: `src/components/layout/header.tsx`의 `navItems`와 메뉴 표시 조건
- 하단 정보: `src/components/layout/footer.tsx`
- 공개 페이지: `src/app/(public)` 아래의 해당 `page.tsx`

메뉴를 바꾸면 데스크톱·모바일, 비로그인·로그인 상태를 함께 확인합니다. 메뉴를 숨기는 것은 서버의 접근 권한 검사와 별개이므로 새 보호 페이지에는 데이터 조회·변경 단계의 권한 검사도 필요합니다.

### 스타일

**Tailwind CSS**는 `className`에 적는 작은 스타일 규칙을 제공합니다.

| 예시 | 의미 |
| --- | --- |
| `p-4` | 요소 안쪽 여백 |
| `mt-4` | 요소 위쪽 바깥 여백 |
| `text-2xl` | 글자 크기 |
| `font-bold` | 굵은 글자 |
| `flex items-center` | 항목을 나열하고 교차 축 가운데 정렬 |
| `rounded-lg` | 둥근 모서리 |
| `text-sm md:text-lg` | 기본 크기를 적용하고, `md` 기준 이상 화면에서 더 큰 글자 사용 |

기존 디자인 규칙과 공통 컴포넌트를 먼저 확인합니다. 색상·간격을 바꾼 뒤 작은 화면, 키보드 이동, 글자와 배경의 대비도 확인합니다.

새 페이지를 만드는 실습은 [첫 실행](getting-started/first-run.md)에 있습니다. 공통 버튼을 바꾸는 작업은 여러 페이지에 영향을 주므로 [난이도별 작업 안내](contributing/tasks-by-level.md)에서 적절한 범위를 고릅니다.

### 맞춤법 검사 명령의 범위

`npm run spell-check`는 `src/**/*.tsx`에서 추출한 문자열을 외부 맞춤법 서비스로 검사합니다. DB의 게시글이나 모든 문서를 검사하는 명령은 아닙니다. 공개해도 되는 코드 문구에만 사용하고, 개인정보나 비공개 문장을 보내지 않습니다.

`npm run spell-fix`는 소스 파일을 수정하므로 사용 후 반드시 diff를 읽고 표현과 코드가 올바른지 확인합니다.

## 5. 관리자 계정과 운영 콘텐츠

### 역할 이해하기

| 역할 | 기본 의미 |
| --- | --- |
| `PENDING` | 소셜 로그인 후 승인 대기 중인 계정 |
| `MEMBER` | 승인된 회원 |
| `FACULTY` | 교수진 역할. 홈페이지 자료 접근과 학사 업무 권한은 별도 정책을 따릅니다. |
| `ADMIN` | 홈페이지 콘텐츠·회원 등을 관리하는 역할 |

홈페이지 `ADMIN`이라는 이유만으로 학사 승인·출석 처리 권한을 모두 갖는 것은 아닙니다. 학사 승인자, 지도교수, 조교 등은 [학사 관리 로드맵](ACADEMIC-MANAGEMENT-ROADMAP.md)과 [AGENTS.md](https://github.com/yeongseon/hra-website/blob/main/AGENTS.md)의 경계를 확인합니다.

이미 관리자가 있다면 신규 개발자가 스크립트로 임의 승격하지 않고, 운영 담당자가 회원 관리 화면에서 필요한 역할을 지정합니다. 권한이 예상과 다르면 선택한 계정과 역할, 변경 후 세션 상태를 확인합니다.

### 첫 관리자 생성 — 운영 담당자용

`seed-admin`은 DB에 관리자 계정을 **실제로 생성하거나 변경하는** 스크립트입니다. 사이트 설치 담당자가 연결 대상·권한·백업 정책을 확인한 상태에서만 사용합니다.

먼저 [DB 변경 절차](developer/database-change-procedure.md)에 따라 필요한 테이블과 함수를 준비하고, [요청 제한 설정](operations/rate-limits.md)도 확인합니다. [설정 파일 우선순위](getting-started/clone-and-setup.md)를 확인해 앱과 관리 명령이 같은 개발·운영 대상을 가리키는지 구분합니다. 그 뒤 대상 환경의 비공개 `.env`에 다음 항목을 설정합니다.

```dotenv
ADMIN_EMAIL=
ADMIN_NAME=
ADMIN_PASSWORD=
```

승인된 관리자 이메일·이름과 비밀번호 관리 도구로 만든 충분히 긴 무작위 비밀번호를 채웁니다. 비밀번호를 명령줄에 직접 넣으면 명령 기록에 남을 수 있으므로 파일을 사용합니다. 운영 `.env`와 개발 `.env`를 혼동하지 않습니다.

새 계정을 만들 때 실행합니다.

```bash
npm run seed-admin -- --confirm-create
```

`--confirm-create`는 적용 확인 플래그이며 미리보기 옵션이 아닙니다. 이미 존재하는 일반 계정을 승격하려면 `ADMIN_EMAIL`과 정확히 같은 주소를 `--confirm-promote=...`에 명시해야 합니다. 이 작업은 역할만 바꾸는 것이 아니라 **비밀번호도 설정하고 기존 세션을 무효화**하므로 일반적인 역할 변경에는 관리자 화면을 우선합니다.

이미 `ADMIN`인 계정은 이 스크립트로 비밀번호가 바뀌지 않습니다. 로그인 복구가 필요하면 담당자가 계정 상태와 승인된 복구 절차를 확인합니다. 임의 SQL로 역할·비밀번호를 바꾸는 절차는 사용하지 않습니다.

생성 후 대상 사이트의 `/admin/login`에서 로그인하고 관리자 화면 접근을 확인합니다. 스크립트 출력에는 계정 정보가 포함될 수 있으므로 공개 PR에 원문 로그를 붙이지 않습니다.

### 콘텐츠 관리

공지·교수진·기수·갤러리·자료는 각각의 관리자 화면에서 편집합니다. 저장 후 공개 화면의 제목·내용·이미지·권한을 확인합니다.

현재 자체 지원서 폼과 제출 데이터는 DB를 사용합니다. 모집 안내에는 외부 접수 링크를 설정할 수도 있으므로, 실제 접수 방식은 해당 모집 설정에서 확인합니다. 관리자 지원서 화면을 구글 시트 자동 연동 화면으로 가정하지 않습니다.

## 6. 검증·배포·운영을 구분하기

- `npm run dev`: 내 컴퓨터에서 빠르게 수정 내용을 확인합니다.
- `npm run typecheck`, `npm run lint`: 타입과 코드 규칙을 검사합니다.
- `npm test`: 저장소가 설정한 테스트를 실행합니다. DB 관련 테스트의 실행 조건과 건너뛴 항목도 확인해야 합니다.
- `npm run build`: 배포용 결과물을 만듭니다. 모든 실제 사용자 동작을 시험하지는 않습니다.
- PR의 CI와 Preview: 자동 검사와 배포 미리보기에서 변경을 확인합니다.
- Production 확인: 승인된 배포 후 실제 운영 환경의 연결과 기능을 확인합니다.

**Preview**는 PR 등의 변경을 확인하는 배포 환경이고, **Production**은 실제 사용자가 이용하는 운영 환경입니다. 같은 코드라도 환경 변수·DB 구조·외부 서비스 설정이 다르면 결과가 달라질 수 있습니다. 필요한 검사와 기록 방법은 [빌드·배포 가이드](contributing/build-and-deploy-safety.md)에 정리되어 있습니다.

막혔다면 실행 명령, 대상 환경, 처음 나타난 원인 오류, 재현 순서를 기록합니다. 비밀값을 지운 뒤 담당자에게 공유하고, 오류를 없애려고 타입 검사를 무시하거나 운영 설정을 임의로 바꾸지 않습니다.
